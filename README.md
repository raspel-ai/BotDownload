# BotDownload v1

Telegram-сервис для видео YouTube, Instagram и TikTok; интерфейс на русском.
Два постоянных процесса: `tgbot.service` и `tgbot-worker.service`, один UID `tgbot`.
Только бот работает с SQLite. Worker выполняет inspect, yt-dlp и FFmpeg.
Транспорт — приватный Unix socket, JSON Lines v1, максимум 64 КиБ.

Нормативные документы: [ТЗ](docs/TECHNICAL_SPEC_V1.md) и
[политика безопасности](docs/SECURITY_POLICY_V1.md). Политика имеет приоритет.
README описывает эксплуатацию, не добавляет новых продуктовых требований.

**Статус: ветка разработки, публичный запуск пока не разрешён.**
Локально проверяются IPC, очереди, состояние, отмена, реальная обработка локальных
MP4/MP3 и транспорт Telegram с тестовыми ответами. Приёмка постоянных юнитов,
реальных платформ, Telegram и Debian 12/Fake-IP требует VPS и токена; без её
фактического выполнения безопасная реальная загрузка не объявляется включённой.
Протокол результатов: [VALIDATION.md](docs/VALIDATION.md).
Продолжение работы: [IMPLEMENTATION_PROGRESS.md](docs/IMPLEMENTATION_PROGRESS.md).

## Устройство и поведение

`Telegram → validate_url → SQLite/карточка → диспетчер → socket → worker →
проверенный файл → выбранный Telegram API → транзакция SQLite → очистка`.

- Исходная ссылка проверяется локально, без DNS и раскрытия redirects. Только
  HTTPS, точные домены и пути из ТЗ. Для YouTube принимаются `/watch?v=ID`,
  `/shorts/ID` и `youtu.be/ID` (ID — ровно 11 символов `[A-Za-z0-9_-]`).
  У коротких ссылок и Shorts разрешён только необязательный `si`; у `/watch` —
  обязательный `v` и необязательные `list`, `start_radio=1` (только вместе с `list`).
  `si`/`list` — 1–128 символов `[A-Za-z0-9_-]`; порядок ключей свободный, дубли,
  пустые значения и повреждённый query отклоняются. После проверки **всего** исходного
  URL сохраняется и передаётся дальше только `https://www.youtube.com/watch?v=ID`;
  вспомогательные параметры не доходят до worker/yt-dlp и не разрешают плейлисты.
  Неизвестные параметры, включая `t`, `index`, `feature`, `utm_*`, вызывают отказ,
  а не удаляются молча. У Instagram/TikTok query запрещены по-прежнему.
  Явный `:443`, percent-encoding, не-ASCII, userinfo, пробелы, управляющие символы,
  обратная косая черта и даже пустой `#` запрещены. При превышении 2048 символов
  URL также отклоняется. Нормализация не выполняет DNS/HTTP и не раскрывает редиректы.
- Одна загрузка/обработка; параллельные inspect ограничены `worker.max_inspects`.
  По умолчанию до 20 ожидающих загрузок, FIFO с временным пропуском при нехватке
  диска; исходное время ожидания не сбрасывается. Отправка идёт независимо.
- Карточки независимы. Callback содержит только код качества; владелец,
  сообщение, доступный вариант и состояние сверяются с SQLite. Повторный полный
  inspect при нажатии не выполняется. Недостоверные качества не показываются:
  при неудачном анализе доступны только «Скачать видео» / «Скачать аудио».
  Если не подтверждена сама защита worker, задача прекращается с диагностикой.
- Цели выбора — 480p/720p/1080p. Сначала закрепляются точные допустимые
  совпадения, затем выбираются ближайшие реальные разрешения в любую сторону.
  Максимум три уникальных видеоформата плюс MP3; подпись показывает фактическую
  короткую сторону, включая портретное видео. При коллизии максимизируется число
  вариантов, затем минимизируется суммарное отклонение; при равенстве предпочтительно
  меньшее разрешение. Русская аудиодорожка предпочтительна, иначе оригинальная;
  отдельный аудиопоток имеет приоритет перед видеофайлом с той же дорожкой.
- Для каждого варианта сохраняются конкретные потоки и параметры обработки.
  Исчезнувший поток требует повторного анализа; автоматической подмены нет.
  После обработки проверяются разрешение, обе стороны кадра, формат, размер,
  продолжительность и целостность. Результат: MP4 H.264/AAC-LC или MP3 VBR `q:a=0`.
- Размеры оцениваются отдельно: совместимые потоки при remux дают приблизительную
  оценку, готовый к побайтовому копированию совместимый MP4 — известный размер.
  При отсутствии обоснованной оценки (включая VBR MP3 и перекодирование) выводится
  «Размер неизвестен». Предварительная оценка не гарантирует успешную отправку.
  Верхний битрейт MP3 используется для планирования диска, не как средний размер.
- Используется только `telegram.max_upload_size_mb[telegram.api_mode]`, без
  дополнительных коэффициентов. Достоверно слишком большие варианты исключаются
  до выбора; если исключены все — кнопок скачивания нет. Неизвестный или
  пограничный размер не считается превышением. Фактический размер проверяется
  перед отправкой; при превышении предлагаются оставшиеся варианты без повторного
  предложения неудачного. Кэш различает потоки, дорожку, фактическое разрешение
  и параметры результата; перед отправкой `file_id` проверяются сохранённые
  фактические сведения и актуальный лимит выбранного API.
- Изменяемые настройки — `config.yaml`, секрет Telegram — `.env`. Worker не
  загружает `.env`; задания не содержат токенов, proxy, cookies или произвольных путей.
- По умолчанию API `cloud`; `local` выбирается явно. `cloud` использует только `https://api.telegram.org`.
  Автоматического переключения нет. Локальный Bot API Server устанавливается
  оператором отдельно и не входит в поставку. `aiogram` использует `is_local=True`;
  файлы отправляются multipart, абсолютные локальные пути не превращаются в URL.
- Квота — 3 подтверждённых новых выдачи за UTC-сутки; `trusted_users` не ограничены.
  Кэш по точному варианту не тратит квоту. `file_id` сохраняется транзакционно.
  Неудачи/отмены не списываются. Повторный результат Telegram при аварии возможен,
  двойное списание по одной задаче исключено ключом SQLite.
- `/start`, `/myid`, `/cancel_all`. Для пользователей вне `trusted_users` первые
  пять попыток ссылок за 600 секунд разрешены, шестая блокирует новые ссылки на 3600 секунд. Состояние сохраняется.
  Команды и обычный текст не расходуют этот лимит.
- По отдельному поручению владельца `trusted_users` освобождены и от дневной квоты,
  и от лимита ссылок/временной блокировки. Их попытки ссылок не учитываются;
  ранее записанная блокировка игнорируется, пока ID входит в список. После изменения
  `trusted_users` перезапустите бот. Старые записи попыток и блокировок не удаляются
  автоматически при добавлении ID. Защита от повторных updates, проверка URL,
  очередь, диск, длительность/размер файлов, ограничения Telegram API и безопасность
  worker действуют для доверенных пользователей. Значения `rate_limit` не меняются.
  Это явно разрешённое исключение из прежнего правила ТЗ §11/§17; сами нормативные
  документы не редактируются.

## Проверенные версии

Целевая система — Debian 13, Python 3.13 (в локальной проверке 3.13.5).
FFmpeg/ffprobe — системный пакет Debian; локально 7.1.5. Прямые зависимости:
`aiogram 3.22.0`, `yt-dlp 2026.10.26`, `yt-dlp-ejs 0.8.0`, `deno 2.9.8`,
`PyYAML 6.0.2`, `python-dotenv 1.1.1`. Полный набор Python-зависимостей фиксируется
в `requirements.lock`. Deno устанавливается в venv; скрипты с CDN во время задания
не скачиваются. Плагины yt-dlp, пользовательские конфиги и автообновления отключены.
Обновляет зависимости только администратор через проверяемое изменение lock-файла.

## Порядок самостоятельной приёмки

**Стандартный режим Telegram API — `cloud`**, официальный `https://api.telegram.org`.
Он задан в `config.yaml`; `local` поддерживается при явном выборе и требует
отдельно установленного Local Bot API Server. Нормативные документы не редактировались:
в них ещё указан default `local`, что расходится с текущим операционным значением
`cloud` по решению владельца. Это расхождение требует отдельного согласования.

На Debian 12 (Python 3.11.2) проведена частичная фактическая приёмка cloud:
подтверждены изоляция постоянного worker, запуск обеих служб, выдача видео
через Telegram и повторная выдача из кэша. Полная приёмка всех сценариев,
Debian 13 и local API пока не подтверждена; подробности в
[журнале приёмки](docs/CLOUD_ACCEPTANCE.md).

Приёмка идёт через SSH небольшими шагами: команда → обезличенный результат →
разбор → следующий шаг. Не выполняйте весь справочник одним скриптом. SSH-доступ
и токен разработчику не требуются; `.env` остаётся только на сервере.
Первый шаг и журнал этапов: [CLOUD_ACCEPTANCE.md](docs/CLOUD_ACCEPTANCE.md).
Ни установка, ни диагностический helper сами по себе не означают PASS внешней приёмки.

## Новая установка на Debian 13

Команды ниже выполняются на VPS после проверки PR. Не вводите настоящий токен
в чат, командную строку, Git или отчёт. При использовании другого пути вместо
`/opt/botdownload` измените **оба unit-файла** (WorkingDirectory и ExecStart);
менять Python-код не требуется.

1. В SSH-терминале под администратором установите системные зависимости.
   Ожидается успешная установка Python/venv и FFmpeg из репозиториев Debian.

   ```bash
   sudo apt update
   sudo apt install python3 python3-venv ffmpeg git curl ca-certificates nano
   ```

2. Там же создайте отдельного непривилегированного пользователя без входа и каталог.
   Это команды только для новой установки. Если пользователь, каталог, Git-копия
   или юниты уже существуют, остановитесь для инвентаризации: не выполняйте повторные
   clone/useradd, не меняйте владельцев рекурсивно и не перезаписывайте файлы.

   ```bash
   sudo useradd --system --no-create-home --home-dir /opt/botdownload --shell /usr/sbin/nologin tgbot
   sudo install -d -o root -g root -m 755 /opt/botdownload
   ```

3. Получите код от имени администратора. Исходники и `.venv` не должны
   принадлежать `tgbot` или быть доступны ему на запись. Ниже указана рабочая ветка; для выпуска следует
   выбрать проверенный коммит. Ожидается чистая рабочая копия без секретов.

   ```bash
   sudo git clone --branch dev/v1-completion https://github.com/raspel-ai/BotDownload.git /opt/botdownload
   ```

4. Перейдите в каталог проекта. Создайте venv и установите зафиксированные зависимости.
   Ожидаются отсутствие ошибок pip и сообщение об отсутствии конфликтов.

   ```bash
   cd /opt/botdownload
   sudo python3 -m venv .venv
   sudo .venv/bin/python -m pip install -r requirements.lock
   sudo .venv/bin/python -m pip check
   ```

   Код и venv остаются у администратора. **До первого запуска любой службы**
   создайте только рабочие каталоги, включая `logs`: бот не сможет создать его
   в root-owned корне. Существующие каталоги сначала проверьте; при symlink или
   неожиданном владельце остановитесь. Не выполняйте рекурсивный chown проекта.
   Команда сохраняет содержимое каталогов и не меняет владельца исходников/venv.

   ```bash
   sudo install -d -o tgbot -g tgbot -m 0700 /opt/botdownload/data /opt/botdownload/data/tmp /opt/botdownload/logs /opt/botdownload/backups /opt/botdownload/files
   sudo stat -c '%n %U:%G %a' /opt/botdownload/logs
   ```

   Ожидается `/opt/botdownload/logs tgbot:tgbot 700`. При ошибке не запускайте
   службы: проверьте путь, владельца и права, не открывая запись на весь проект.

5. Скопируйте пример секрета и заполните файл **локальным редактором на VPS**.
   Не публикуйте содержимое. `.env` должен читаться только `tgbot`.
   Если любой из двух `test` ниже завершается с ошибкой — остановитесь: существующий
   `.env` сохраняется, повторное копирование запрещено.

   ```bash
   sudo -u tgbot test ! -e .env
   sudo -u tgbot test ! -L .env
   sudo install -o tgbot -g tgbot -m 600 .env.example .env
   sudo -u tgbot nano .env
   ```

6. Локально отредактируйте `config.yaml`: `admin_telegram_id`, `trusted_users`, режим
   API и его адрес, лимиты, хранение. Для текущей приёмки задайте `api_mode: cloud`,
   `api_base_urls.cloud: "https://api.telegram.org"`, `max_upload_size_mb.cloud: 50`.
   Поле local остаётся в схеме, но ни Local Server, ни подключение к нему пока не нужны. Не публикуйте реальные ID. `files_dir` — отдельный
   относительный приватный каталог, по умолчанию `files`. `worker.socket` одинаков
   у обоих сервисов, по умолчанию `/run/botdownload/worker.sock`; не `/tmp`.

   ```bash
   sudo chown tgbot:tgbot config.yaml
   sudo -u tgbot chmod 600 config.yaml
   sudo -u tgbot nano config.yaml
   sudo -u tgbot .venv/bin/python scripts/check_installation_permissions.py
   sudo -u tgbot .venv/bin/python -m bot.admin doctor
   ```

   Ожидается PASS конфигурации и зависимостей. Эта команда **не доказывает** сетевую
   изоляцию. Ошибки конфигурации называют параметр и причину, не секретное значение.

7. Установите два постоянных юнита от администратора. Затем обязательно задайте
   ограничения памяти, CPU и процессов соразмерно вашему VPS. Команды копирования
   ниже допустимы только при отсутствии прежних unit/drop-in: если они уже есть,
   сначала сохраните их и разберите отличия; слепая замена запрещена. Пример не является
   требованием иметь определённый объём RAM или диска.

   ```bash
   sudo install -o root -g root -m 644 deploy/tgbot.service /etc/systemd/system/tgbot.service
   sudo install -o root -g root -m 644 deploy/tgbot-worker.service /etc/systemd/system/tgbot-worker.service
   sudo mkdir -p /etc/systemd/system/tgbot-worker.service.d
   sudo cp deploy/resources.conf.example /etc/systemd/system/tgbot-worker.service.d/resources.conf
   sudo nano /etc/systemd/system/tgbot-worker.service.d/resources.conf
   sudo systemctl daemon-reload
   sudo systemd-analyze verify /etc/systemd/system/tgbot.service /etc/systemd/system/tgbot-worker.service
   ```

8. **До реальных inspect/download выполните приёмку защиты**, описанную ниже.
   Отсутствие поддержки cgroup-BPF/IPAddressDeny или совместимого DNS означает
   остановку включения загрузки, а не снятие запрета. Не запускайте worker через
   `sudo`, `systemd-run`, namespace-обходы или как дочерний процесс бота.

9. После проверки включите автозапуск и оба сервиса. Ожидаются два активных процесса
   под UID `tgbot`; бот отправляет администратору уведомление, когда Telegram доступен.

   ```bash
   sudo systemctl enable tgbot-worker.service tgbot.service
   sudo systemctl start tgbot-worker.service tgbot.service
   sudo systemctl status tgbot-worker.service tgbot.service
   ```

   При недоступном выбранном Bot API бот повторяет соединение с экспоненциальной
   задержкой 1–300 секунд, не меняя режим. Проверьте также отвечающий `/myid`.

## Приёмка защиты на каждом VPS

Используется один и тот же постоянный `tgbot-worker.service` во время испытания и
эксплуатации. В нём уже есть `ExecStartPre=... bot.probe --if-requested`.
**Не добавляйте временный ExecStartPre через edit и не меняйте unit после пробы.**
Без root-owned запроса `/run/botdownload-probe.request` эта проверка не обращается
в сеть и не выдаёт допуск. Реальные inspect/download по-прежнему требуют отдельного
root-owned подтверждения `/etc/botdownload/worker-isolation.json`.

Согласованная политика не меняется: только `127.0.0.0/8` и `::1/128` запрещены для
worker/детей. Остальные private/link-local/metadata/Fake-IP адреса не блокируются;
DNS и маршруты не меняются. `PrivateNetwork=yes` и обходы через transient units
не используются. Бот остаётся в отдельном cgroup с доступным loopback.

Процедура ниже — справочник для пошаговой приёмки. Каждый переход выполняется
после разбора результата предыдущего шага, без автоматического ответа yes.

1. Остановите оба сервиса. Проверьте содержимое установленного юнита и выбранные
   ограничения ресурсов. Существующие данные, конфигурация и прежние подтверждения
   не удаляются. Если есть старое подтверждение, сначала отдельно согласуйте его
   архивирование/отзыв: helper не перезаписывает его автоматически.

2. Администратор устанавливает **проверенные копии** helper и его stdlib-модуля в
   каталог root. Сначала сверяются коммит и SHA-256 исходников с проверенной версией;
   после копирования SHA-256 сверяются повторно (эталоны для этой редакции —
   в CLOUD_ACCEPTANCE.md). Исходники нельзя менять между
   сверкой и установкой. Для существующих копий сначала сохранить предыдущую версию.

   ```bash
   sudo install -d -o root -g root -m 755 /usr/local/libexec/botdownload
   sudo install -o root -g root -m 644 scripts/confirm_worker_isolation.py /usr/local/libexec/botdownload/confirm_worker_isolation.py
   sudo install -o root -g root -m 644 bot/isolation.py /usr/local/libexec/botdownload/isolation.py
   sudo sha256sum /usr/local/libexec/botdownload/confirm_worker_isolation.py /usr/local/libexec/botdownload/isolation.py
   ```

   Для подтверждения root **не запускает** `.venv/bin/python` и скрипты из доступной `tgbot` на запись
   копии. Helper использует системный Python в isolated mode и загружает только
   проверенную root-owned копию `isolation.py`; проверяет владельцев и права родителей.

3. Подготовьте запрос с уникальным не секретным идентификатором. Это создаёт только
   новый файл диагностики, **не включает загрузку**. При существующем запросе helper
   откажет; его не удаляют вслепую, а сначала разбирают и архивируют результаты.

   ```bash
   sudo /usr/bin/python3 -I /usr/local/libexec/botdownload/confirm_worker_isolation.py --prepare
   ```

4. По инструкции следующего шага создайте **новый приватный пустой тестовый каталог**,
   принадлежащий `tgbot`, и только файл `botdownload-probe.txt` с идентификатором из
   запроса. В двух отдельных SSH-терминалах запустите стандартный Python HTTP Server
   под `tgbot`: IPv4 `127.0.0.1:18765` и IPv6 `[::1]:18765`, с `--directory` именно
   этого тестового каталога. Не раздавайте проект, `.env`, базу или пользовательские
   файлы. Не используйте отсутствующий `/var/empty` как якобы успешный baseline.

   Подтвердите HTTP 200 и правильный идентификатор обоих серверов **вне worker**,
   под UID `tgbot`. Оставьте оба сервера работающими непрерывно до подтверждения.
   Если IPv6, порт или baseline недоступны, результат INCONCLUSIVE; допуск не выдаётся.

5. После работающего baseline перезапустите только постоянный worker и проверьте
   его журнал. Проба выполняется в том же cgroup и формирует приватный отчёт
   `/run/botdownload/isolation-probe.json`. Она проверяет прямые соединения IPv4/IPv6
   родителя и дочернего процесса, затем системный DNS и HTTPS с проверкой сертификата.
   Для HTTP(S) пробы proxy не используется, DNS и маршруты не подменяются.

   `ECONNREFUSED`, отсутствие IPv6/маршрута и отсутствующий listener дают
   **INCONCLUSIVE**, а не PASS фильтра. Доступный loopback даёт FAIL. Наблюдённые
   блокировки и работающие DNS/HTTPS дают `OBSERVED`, ещё не итоговую приёмку.
   При ошибке остановите worker, сохраните вывод и разберите причину;
   не снимайте IPAddressDeny. Не редактируйте unit после успешной пробы.

6. Администратор запускает установленный helper без `--prepare`:

   ```bash
   sudo /usr/bin/python3 -I /usr/local/libexec/botdownload/confirm_worker_isolation.py
   ```

   Он требует свежий полный отчёт текущего boot, unit/drop-in и InvocationID,
   проверяет effective-настройки (включая отсутствие IPAddressAllow), повторно
   получает оба baseline под UID `tgbot` вне worker и только после этого спрашивает
   `VERIFIED-PERMANENT-WORKER`. Enter отменяет. После ответа настройки и baseline
   проверяются повторно. Только тогда создаётся новый root-owned файл допуска.
   Существующий файл не перезаписывается.

7. Сохраните запрос, отчёт, effective-настройки и обезличенный журнал как доказательства.
   **Архивируйте созданный запрос из `/run/botdownload-probe.request`**, чтобы следующие
   обычные рестарты не требовали HTTP-фикстур; пользовательские данные не затрагиваются.
   Не изменяйте unit/drop-in после испытаний. Два временных HTTP-сервера остановите
   Ctrl+C. Подтверждение действует только в текущем boot для проверенного unit;
   после перезагрузки/изменений проводится новая проба с сохранением старых доказательств.

8. После подтверждённой защиты запускается `tgbot.service` в **cloud** и проверяется
   реальный цикл. Local Bot API и Debian 12/Fake-IP идут отдельными следующими этапами.
   Без фактических результатов внешние проверки остаются INCONCLUSIVE.

Остаточные риски не изменились: один UID не изолирует секреты от скомпрометированного
worker; полная защита SSRF в v1 не заявляется. Root-подтверждение — решение оператора
на основании испытаний, а не доказательство безопасности само по себе.

## Диагностика и файлы

Из `/opt/botdownload` под `tgbot` доступны команды без токена в аргументах:

```bash
sudo -u tgbot .venv/bin/python -m bot.admin --help
sudo -u tgbot .venv/bin/python -m bot.admin status
sudo -u tgbot .venv/bin/python -m bot.admin queue
sudo -u tgbot .venv/bin/python -m bot.admin disk
sudo -u tgbot .venv/bin/python -m bot.admin cache
sudo -u tgbot .venv/bin/python -m bot.admin errors
sudo -u tgbot .venv/bin/python -m bot.admin db status
sudo -u tgbot .venv/bin/python -m bot.admin db backups
sudo -u tgbot .venv/bin/python -m bot.admin db check
sudo -u tgbot .venv/bin/python -m bot.admin db backup
```

Справка каждой подкоманды: `python -m bot.admin <подкоманда> --help`.
Для просмотра логов из каталога проекта: `tail -F logs/bot.log`; Ctrl+C завершает
только просмотр. Ротация по `logging`; логи не содержат токенов и полных URL.

SQLite — `data/bot.sqlite`, содержит текущие карточки, состояния задач/отправки,
идемпотентность updates, попытки, UTC-квоты, блокировки и кэш `file_id`.
Рабочие данные не являются отдельной пользовательской историей скачиваний.
Резервные копии находятся в `backups/`, создаются SQLite Backup API каждые 24 часа
и перед миграцией/обновлением, проверяются; остаётся до `backup.max_copies`.
Повреждённые базы `data/database_corrupt_*.sqlite` сохраняются отдельно и не
удаляются автоматически. Секреты, БД, копии, логи и медиа исключены из Git.

Временные каталоги — `data/tmp/<execution_id>/`, готовые результаты — `files/`.
Каталоги `files` и `data/tmp` должны находиться на одной файловой системе;
worker проверяет это при старте. Манифест рядом с результатом содержит размер, длительность, формат, SHA-256 и
подтверждение проверки worker. Бот сверяет его и файл перед отправкой; FFmpeg в
боте не запускается. При `keep_downloaded_files: true` успешный результат остаётся
в приватном `files/`; при `false` удаляется. Незавершённые/повреждённые файлы не
сохраняются этой настройкой; готовый результат ожидающей повторной отправки сохраняется.
После окончательной ошибки отправки результат удаляется в обоих режимах.

Для инвентаризации/очистки сиротских временных каталогов **сначала остановите оба
сервиса**. CLI удерживает блокировки обоих компонентов, чтобы исключить гонку.
Успешно сохранённые медиа не входят в автоматическую или сиротскую очистку.

```bash
sudo systemctl stop tgbot.service tgbot-worker.service
sudo -u tgbot .venv/bin/python -m bot.admin tempfiles list
sudo -u tgbot .venv/bin/python -m bot.admin tempfiles clean --dry-run
sudo -u tgbot .venv/bin/python -m bot.admin tempfiles clean
```

Последняя команда покажет список и запросит `yes`; Enter/no отменяет удаление.
Администратор отдельно принимает решение об удалении сохранённых успешных результатов,
старых операционных записей и архивов повреждённой БД; автоматически по возрасту они
не удаляются. Перед удалением операционных данных сохраните проверенную резервную
копию и остановите сервисы; полное обнуление доступно только через подтверждённый `db init`.

Ручная диагностика бота из корня: `.venv/bin/python -m bot` под `tgbot`, когда
штатный бот остановлен. Она не запускает worker. `.venv/bin/python -m bot.worker`
вне постоянного защищённого юнита может обслуживать диагностику IPC, но реальные
inspect/download будут отклонены. Никогда не снимайте защиту ради ручного теста.

## Безопасное обновление

1. В SSH-терминале перейдите в `/opt/botdownload`. Проверьте ветку, чистоту копии
   и доступ к GitHub. Если есть локальные изменения исходников/config, остановитесь
   и сохраните их отдельно; не используйте `reset --hard` или `git clean`.

   ```bash
   cd /opt/botdownload
   sudo git status --short --branch
   sudo git ls-remote origin
   ```

2. Остановите оба сервиса и проверьте завершение процессов. Worker останавливает
   группы yt-dlp/FFmpeg, systemd завершает остаток cgroup; данные SQLite сохраняются.

   ```bash
   sudo systemctl stop tgbot.service tgbot-worker.service
   sudo systemctl status tgbot.service tgbot-worker.service
   ```

3. Создайте проверенную копию SQLite штатной командой (не `cp` открытой базы).
   Для старой версии без такой команды сначала сделайте SQLite Backup API из
   остановленного проекта под `tgbot` в отдельный защищённый каталог; проверьте
   `PRAGMA integrity_check`. Не изменяйте оригинал и не создавайте фиктивную копию.

   ```bash
   sudo -u tgbot .venv/bin/python -m bot.admin db backup
   sudo -u tgbot .venv/bin/python -m bot.admin db check
   ```

4. Запишите текущий коммит **вне заменяемого дерева кода**, например в ваш журнал
   обслуживания. Он нужен для отката. Сохраните локально `.env` и `config.yaml` с
   приватными правами; не добавляйте их в Git.

   ```bash
   sudo git rev-parse HEAD
   ```

5. Получите проверенное обновление. `fetch` сам не заменяет рабочие файлы.
   Затем подставьте выбранный проверенный SHA вместо `ПРОВЕРЕННЫЙ_SHA`.
   `.env`, БД, backups, files и logs не затрагиваются. Если Git сообщает конфликт
   локального config.yaml, остановитесь и вручную совместите настройки по образцу
   новой версии. Не перезаписывайте свои ID/endpoint/секреты образцом.

   ```bash
   sudo git fetch origin
   sudo git switch --detach ПРОВЕРЕННЫЙ_SHA
   ```

6. Обновите зависимости от имени администратора и проверьте конфигурацию.
   До запуска проверьте рабочие каталоги, включая `logs`. Для отсутствующего logs:
   `sudo install -d -o tgbot -g tgbot -m 0700 /opt/botdownload/logs`.
   Существующие каталоги сначала проверьте; не выполняйте рекурсивный chown
   исходников или `.venv`. Локальный явный выбор `api_mode` при обновлении сохраняется. При переходе с прежней ветки
   удалите `storage.download_dir` из локального YAML и задайте `files_dir`,
   `keep_downloaded_files` и раздел `worker` по текущему образцу. Старые алиасы не
   поддерживаются. Старые таблицы/файлы сохраняются; квоты, блокировки и задачи
   переносятся после проверенной копии. Ранее не проверенные файлы не отправляются
   без нового защищённого приготовления. Не удаляйте прежний каталог медиа вручную
   до инвентаризации и завершения переноса.

   ```bash
   sudo .venv/bin/python -m pip install -r requirements.lock
   sudo .venv/bin/python -m pip check
   sudo -u tgbot .venv/bin/python -m bot.admin doctor
   ```

7. Установите обновлённые юниты, сохраните свои drop-in ресурсов. Выполните daemon-reload,
   проверку защиты постоянного worker и новое подтверждение, если unit изменился.
   Затем запустите worker и бот в этом порядке.

   ```bash
   sudo systemctl start tgbot-worker.service tgbot.service
   sudo systemctl status tgbot-worker.service tgbot.service
   ```

8. Проверьте `/myid`, состояние очереди, восстановленные готовые файлы и логи.
   Администратору приходит уведомление о старте. Обычные ошибки отдельных ссылок
   не вызывают отдельных административных сообщений.

## Восстановление базы и откат

При повреждении обработка прекращается, повреждённые файлы сохраняются, последняя
проверенная совместимая копия восстанавливается с повторной проверкой. При отсутствии
исправной копии пустая база автоматически не создаётся, даже при следующем старте.

Для ручного восстановления остановите **оба** сервиса; сохраните исходные повреждённые
файлы и все копии отдельно. Работайте с копиями, не экспериментируйте с оригиналом.
Из каталога проекта под `tgbot` сначала просмотрите проверки, затем выберите файл
внутри `backups`:

```bash
sudo -u tgbot .venv/bin/python -m bot.admin db restore --list
sudo -u tgbot .venv/bin/python -m bot.admin db restore --backup ИМЯ_КОПИИ.sqlite
```

CLI откажет при работающем боте; покажет путь/дату/проверку, предупредит о потере
изменений после копии и запросит `yes`. Enter/no отменяет операцию. Текущая база
сохраняется отдельно; восстановленная проверяется повторно.
Если исправных копий нет, `db init` доступен только после осознанного подтверждения:

```bash
sudo -u tgbot .venv/bin/python -m bot.admin db init
```

Он предупреждает, что квоты, блокировки, очередь и кэш не восстановятся, сохраняет
имеющиеся файлы отдельно и требует `yes`. Секреты и медиа эта команда не удаляет.

Если обновление не работает, остановите оба сервиса, верните сохранённый SHA кода
через `git switch --detach`, восстановите соответствующие зависимости и проверьте
совместимость схемы. Не откатывайте SQLite автоматически. При необходимости отдельно
выберите проверенную копию с предупреждением о потере новых изменений и явным
подтверждением. Сохраните конфигурацию установленного сервиса и повторно проверьте
защиту worker до реальных загрузок.

## Тесты разработки

Из корня проекта с установленными зависимостями:

```bash
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m pytest -q
```

Тесты используют временные каталоги, локальные синтетические медиа и тестовый Telegram.
Они не используют настоящий токен и не выполняют незащищённую загрузку с платформ.
Публичная приёмка требует всех внешних сценариев из протокола VALIDATION.md.
