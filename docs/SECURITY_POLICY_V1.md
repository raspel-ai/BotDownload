# BotDownload — утверждённая политика безопасности v1

Статус: **Редакция v1 с изменениями, согласованными 2026-11-05** (хранение готовых медиафайлов, строгая проверка URL, два systemd-юнита). Исходная политика утверждена 2026-11-03. Это нормативные требования к реализации, а не утверждение, что все механизмы уже работают.

## 1. Пользовательский ввод
- Только одна HTTPS-ссылка на видео YouTube, TikTok или Instagram. Явный список разрешённых доменов, без подстрочного совпадения.
- **До любого `yt-dlp`**, включая inspect, единый диспетчер обязан вызвать `validate_url(raw_url)`: локальный разбор без DNS/HTTP; ровно один URL длиной не более 2048 символов; HTTPS; точный hostname из allowlist; разрешённый путь отдельного видео и валидный идентификатор; допустимые параметры без неоднозначных дублей. Отклонять credentials, явный порт, IP-literal, фрагменты, пробелы и управляющие символы, плейлисты, сокращатели вне allowlist и неподдерживаемые объекты. При отказе `yt-dlp` не запускается.
- Успешная проверка создаёт типизированный `ValidatedURL` и утверждённое задание; `validate_url` не выполняет сетевых запросов и не заменяет ограничение исходящих соединений.
- Пользователь не задаёт аргументы yt-dlp/FFmpeg, пути, shell-команды, proxy, cookies, HTTP-заголовки или конфигурацию. Все параметры фиксирует сервис.

## 2. Проверяющий диспетчер — обязательная точка допуска
- Все операции inspect/download/cancel проходят через единый логический проверяющий диспетчер, затем worker; Telegram-обработчики не запускают yt-dlp/FFmpeg напрямую.
- Worker исполняет только утверждённые задания, проверяет их целостность и допустимый формат; не принимает произвольные команды, аргументы или пути.
- Никаких штатных путей обхода диспетчера; архитектурные тесты контролируют это.
- Оба режима (метаданные и скачивание) используют общую базовую защиту.

## 3. Метаданные и кнопки
- При поступлении новой ссылки диспетчер локально проверяет исходный URL один раз, без HTTP-переходов и раскрытия перенаправлений; анализирует в worker и сохраняет проверенный URL, доступные форматы, владельца и идентификатор карточки. Запросы `yt-dlp` к API/CDN платформ не ограничиваются пользовательским allowlist доменов; на них распространяются ограничения загрузчика и сетевая политика v1.
- Метаданные: название, автор, длительность, дата, просмотры, обложка, язык, варианты качества, оценка размера. Внешние значения — недоверенные; проверять типы/длины и безопасно отображать. Неточный размер помечать как приблизительный.
- При успешном анализе inline-кнопка передаёт только код реально доступного качества (480p/720p/1080p/MP3, если соответствующий вариант доступен), **не URL**. При неудачном анализе или невозможности определить доступные качества показываются только две кнопки: «Скачать видео» (код `video`) и «Скачать аудио» (код `audio`, итоговый MP3); вымышленные качества не показываются. Диспетчер находит исходный URL по сохранённой карточке и проверяет владельца, сообщение, допустимость качества и состояние задания.
- Повторный полный анализ URL по кнопке не нужен. Перед исполнением проверяется целостность утверждённого задания.
- Новая ссылка создаёт независимую карточку; никогда не заменяет URL предыдущей.

## 4. yt-dlp / FFmpeg
- Только экстракторы YouTube, TikTok, Instagram; без Generic, плейлистов и произвольных сайтов.
- Запуск без shell, аргументы формирует сервис; отключить чтение пользовательских конфигов yt-dlp и динамические плагины/обновления во время задания.
- Допустимые FFmpeg и JS runtime определяет сервис; дочерние процессы подчиняются ограничениям, отмене и тайм-аутам.

## 5. Системная изоляция v1
- **Два постоянных systemd-юнита**: `tgbot.service` (Telegram, диспетчер, SQLite, отправка) и `tgbot-worker.service` (inspect, yt-dlp, FFmpeg); Unix domain socket между ними. **Один отдельный непривилегированный Linux-пользователь `tgbot` для обоих**; без root/sudo/лишних capabilities. Юниты устанавливает администратор, бот не управляет системным systemd и не создаёт transient units.
- Worker и дочерние процессы наследуют ограничения своего systemd cgroup; применяются `NoNewPrivileges=true`, `ProtectSystem=full`, `ProtectHome=true`, `PrivateTmp=true` и подходящие ограничения ресурсов. Ручной запуск допустим для диагностики, но не разрешает незащищённые inspect/download.
- Контролируемые рабочие каталоги, приватные временные каталоги задач, запрет произвольных путей, проверка готового файла (обычный файл, не symlink, размер и расположение), очистка.
- Системные ограничения процессов, памяти, ФС и привилегий без нарушения работоспособности.
- Worker не должен получать Telegram-токен, `.env` или данные SQLite через задания и не должен обращаться к SQLite по протоколу приложения; SQLite открывает, читает и изменяет только основной бот; worker не использует SQLite. **Остаточный риск:** при общем UID это не гарантирует запрет чтения файлов SQLite/секретов на уровне ОС; один UID не защищает секреты бота от скомпрометированного worker и не обеспечивает непреодолимость программного диспетчера.

## 6. Сетевая политика v1
- Для сетевых соединений yt-dlp и дочерних процессов блокировать **только** `127.0.0.0/8` и `::1/128`.
- Остальные частные IPv4/IPv6, link-local, metadata-адреса и Fake-IP `198.18.0.0/15` **не блокировать в v1**.
- Не подменять системный DNS, не задавать IP платформ, не менять маршруты роутера или VPS. YouTube и TikTok могут использовать разные маршруты.
- Не блокировать loopback для самого Telegram-бота и его локального IPC.
- Штатная защита worker — `IPAddressDeny=127.0.0.0/8` и `IPAddressDeny=::1/128` в постоянном `tgbot-worker.service`, отдельно от `tgbot.service`. Если DNS использует loopback, обеспечить совместимость без тихого снятия запрета для загрузчика; DNS через Unix-сокет **не предполагается гарантированным**. Не менять глобальные настройки DNS. Если защита на сервере не может быть применена или DNS/HTTPS не работают при действующей защите, не запускать незащищённую загрузку.
- `PrivateNetwork=yes` не использовать в v1: оно лишает worker обычного выхода в интернет без дополнительной сетевой инфраструктуры. `RestrictAddressFamilies` не заменяет IP-фильтрацию.
- **Остаточный риск:** защита от SSRF неполная; последующие запросы yt-dlp могут обращаться к внутренним адресам.

## 7. Ресурсы и очередь
- Независимые тайм-ауты анализа и загрузки, ограничения памяти, процессов, диска, размеров и длительности.
- Не более одной одновременной загрузки/обработки; `inspect` может асинхронно выполняться параллельно в том же защищённом worker без дополнительных download-worker. Очередь `download` ограничена 20 ожидающими сверх активной задачи, время ожидания — 30 минут; состояния в SQLite ведёт только основной бот.
- При отмене диспетчер направляет команду worker через IPC; worker останавливает всю группу дочерних процессов yt-dlp/FFmpeg и подтверждает результат, после чего бот фиксирует состояние. При ошибке/тайм-ауте останавливать всю группу дочерних процессов, удалять частичные файлы; восстанавливать/завершать прерванные задачи безопасно. При потере связи с worker не объявлять отмену успешно завершённой без подтверждения прекращения процессов.

## 8. Отправка и эксплуатация
- Отправлять только проверенные файлы в выбранном качестве; без молчаливой подмены формата. Соблюдать лимиты Telegram и квоты успешных выдач. Хранение проверенного готового файла после успешной отправки определяется `storage.keep_downloaded_files`: `true` — сохранить в приватном каталоге `botdownload/files`, `false` — удалить (значение по умолчанию).
- Настройка хранения не отключает обязательное удаление частичных загрузок, промежуточных и повреждённых файлов при отмене, ошибке и тайм-ауте. Проверенные готовые файлы, ожидающие повторной отправки, сохраняются до завершения задачи. После окончательно неуспешной отправки результат удаляется в обоих режимах. Сохранённые успешно отправленные файлы не удаляются автоматической очисткой временных задач; их удаление требует отдельного подтверждённого административного действия. Каталог хранения приватный, отдельный от временных каталогов, без публичного доступа и произвольных путей; файлы учитываются в ограничениях диска.
- Не раскрывать пользователям токены, пути, команды, чувствительные данные. Не писать секреты и чувствительные URL в логи без необходимости.
- Зависимости обновляет администратор, не пользовательский запрос; ошибки задач не останавливают сервис.

- Изоляция секретов бота от worker на уровне UID.

## 10. Приёмка
- Тесты допуска URL, параметров, целостности заданий, привязки кнопок и запрета обхода диспетчера.
- Подтверждение реального запрета loopback **в постоянном worker-юните**: доступ к заведомо работающему TCP-сервису на `127.0.0.1` без фильтра и отказ при фильтре; рабочие DNS и HTTPS; отсутствие обхода ограничений дочерними процессами. Проверки 2026-11-05 на двух VPS с transient units показали DNS/HTTPS OK и недоступность локального HTTP-сервиса при фильтре, но не заменяют приёмку штатного worker. Fake-IP должен работать без изменения маршрутов.
- Конечный набор позитивных/негативных тестов `validate_url` и доказательство, что при отказе ни inspect, ни download не вызывают `yt-dlp`.
- Проверка лимитов, отмены, очистки, перезапуска, безопасной отправки; оба значения `storage.keep_downloaded_files` и обязательная защитная очистка в обоих режимах.
- Полный интеграционный цикл: ссылка → метаданные → выбор качества → скачивание → отправка Telegram.
- Проверка на обычном Linux VPS и тестовом Debian 12 с Fake-IP.
- До успешной проверки нельзя заявлять, что реальная загрузка безопасно включена.


## Уточнения v1, согласованные 2026-11-06

- Для готовых медиа используется приватный каталог `botdownload/files` (при необходимости настраиваемый относительно рабочего каталога); частичные и промежуточные файлы хранятся отдельно и подлежат обязательной очистке.
- Ошибка предварительного `inspect` сама по себе не запрещает загрузку: пользователь уведомляется; продолжение допустимо только при сохранении проверок безопасности и без выдуманных метаданных. До отправки проверяются фактические продолжительность (не более 7200 секунд), размер, формат и целостность; превышение лимита требует удаления файла и уведомления.
- Логические типы заданий `inspect` и `download` различаются; не более одной активной загрузки/обработки, максимум 20 ожидающих `download` и 30 минут ожидания; задачи с недостатком диска пропускаются без сброса времени.
- Для двух целевых VPS подтверждена совместимость DNS/HTTPS с запретом loopback. Резервный DNS-механизм в v1 не специфицируется; при несовместимости на другом сервере запрет не отключается и загрузка не запускается.
- Проверяется только исходный пользовательский URL без HTTP-переходов в диспетчере; CDN/API-запросы yt-dlp не ограничиваются пользовательским allowlist, но остаются под сетевыми ограничениями worker.

## 11. Уточнение URL-параметров v1
- Для исходного YouTube URL `/watch` допускается только единственный параметр `v=ID`; у `youtu.be`, Instagram и TikTok query-параметры не допускаются. Любые дополнительные параметры, включая `list`, `t`, `si`, `feature`, `utm_*`, отклоняются без автоматического удаления или сетевого раскрытия ссылки.
- Это ограничение относится только к исходному пользовательскому URL. Запросы экстракторов к API/CDN не обязаны соответствовать пользовательскому allowlist; на них распространяется сетевая политика §6.
- Для рабочего каталога `botdownload` используется `files/` для готовых медиа; пути socket, SQLite и временных файлов выбирает разработчик при установке с соблюдением приватных прав и изоляции systemd.
