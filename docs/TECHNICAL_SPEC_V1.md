## 1. Назначение и возможности бота

Telegram-бот предназначен для скачивания видео и извлечения аудио по ссылкам из:

- YouTube;
- Instagram;
- TikTok.

Для загрузки используется `yt-dlp`, для обработки и конвертации медиа — FFmpeg.

Основные функции:

- принимать ссылки от пользователей;
- анализировать доступное содержимое без предварительного скачивания всего файла;
- показывать информацию о видео и доступных вариантах;
- скачивать выбранный вариант;
- отправлять видео или аудио непосредственно в Telegram;
- обрабатывать несколько ссылок от одного пользователя в отдельных сообщениях;
- использовать очередь задач, кэш и дневные лимиты;
- восстанавливать незавершённые задачи после перезапуска;
- удалять небезопасные и промежуточные временные файлы; хранение готового успешно отправленного медиа регулируется `storage.keep_downloaded_files`.

Интерфейс бота — на русском языке.

## 2. Среда и технологии

| Компонент | Решение |
|---|---|
| Сервер | Debian 13 |
| Язык | Python |
| Изоляция зависимостей | `venv` |
| Скачивание | `yt-dlp` |
| Обработка медиа | FFmpeg |
| База данных | SQLite |
| Конфигурация | `config.yaml` |
| Секреты | `.env` |
| Временные файлы | Локальный диск сервера |
| Отправка файлов | Telegram Bot API в выбранном режиме: `local` или `cloud` |

**Требования к объёму диска сервера не фиксируются в ТЗ.** Бот может быть установлен на разных серверах с разным доступным пространством (например, около 10 ГБ или 2000 ГБ). Разработка ведётся для самого бота, а не для конкретной конфигурации сервера. Проверки свободного места, безопасная остановка при заполнении диска и очистка временных файлов уже определены в разделе 10 и должны работать независимо от общего объёма диска. Готовые медиафайлы сохраняются локально только при `storage.keep_downloaded_files: true`; при `false` удаляются после успешной отправки.

## 3. Запуск и конфигурация

### 3.1. Запуск

Для разработки и диагностики должна сохраняться возможность **ручного запуска Python-компонента без обязательных аргументов** из корневой директории проекта. Штатный рабочий запуск выполняется двумя постоянными systemd-юнитами согласно §3.3.

Предполагаемый пример:

```bash
python -m bot
```

Это пример ручного запуска бота; точная команда зависит от окончательной структуры проекта. Ручной запуск не обязан запускать worker и не разрешает реальный inspect/download вне защищённого `tgbot-worker.service`.

Не нужно передавать через командную строку токен, путь к конфигурации или параметры загрузки.

### 3.2. Конфигурация

Все изменяемые параметры поведения бота хранятся централизованно в `config.yaml`.

Токен Telegram и другие секреты хранятся в `.env`. В репозитории должны быть `.env.example` без настоящих секретов и `.gitignore`, исключающий секреты, базу данных, логи и пользовательские файлы. Выбранные версии Python и зависимостей фиксируются в проекте; README указывает проверенные версии и команды установки.

Хранение успешно отправленных готовых медиафайлов определяется `storage.keep_downloaded_files`; при `true` файлы сохраняются в `botdownload/files`, при `false` удаляются после отправки. Для оперативных записей и резервных копий SQLite документировать, какие данные сохраняются, где они хранятся и как удаляются; не включать пользовательские данные, БД, логи и резервные копии в Git.

При запуске бот должен проверять конфигурацию и обязательные зависимости. При ошибке — выводить понятную причину и завершаться, а не использовать случайные значения по умолчанию.

SQLite используется для динамических данных: задач, очереди, состояния отправки, дневного использования лимитов и кэша. Статические настройки не дублируются в базе.

### 3.3. Запуск и ручная диагностика

- Штатный запуск v1 — два постоянных системных юнита `tgbot.service` и `tgbot-worker.service`, устанавливаемых администратором один раз. Оба работают под одним непривилегированным UID `tgbot`.
- Для разработки, тестирования и диагностики сохраняется возможность ручного запуска компонентов; для реальных `inspect` и `download` worker обязан работать в подтверждённом защищённом контуре. Ручной запуск бота не даёт права запускать незащищённый `yt-dlp`.
- Бот не вызывает `systemd-run`, не создаёт transient units и не получает полномочий управления системным systemd. Ресурсные лимиты юнитов подбираются по VPS, а не фиксируются значениями из примеров.
- После рестарта компоненты сверяют состояние заданий в SQLite и на диске; ошибки worker не должны завершать бот.

## 4. Приём и проверка ссылок

Бот принимает одну ссылку на видео в одном сообщении.

- Если сообщение содержит несколько ссылок, бот отклоняет его и просит отправить каждую ссылку отдельным сообщением.
- Разрешены только домены из закрытого списка ниже. Сравнение имени хоста выполняется точно, без проверки по подстроке и без автоматического разрешения произвольных поддоменов.
- Ссылки на плейлисты не поддерживаются в первой версии.
- Неизвестные домены, некорректные ссылки и недоступные материалы обрабатываются понятным сообщением об ошибке.
- Разрешается только схема `https`. URL с логином/паролем, нестандартным портом, некорректным синтаксисом или другой схемой отклоняется.
- Проверяется **исходный пользовательский URL**, без выполнения HTTP-запросов и раскрытия перенаправлений в диспетчере. Запрещённые короткие домены отклоняются сразу, независимо от возможного назначения перенаправления. Запросы экстракторов `yt-dlp` к API, CDN и медиаресурсам не ограничиваются allowlist исходных пользовательских доменов; на них распространяются ограничения самого загрузчика и сетевая политика §23.2.
### 4.0. Обязательная локальная `validate_url(raw_url)`

До **любого** вызова `yt-dlp`, включая получение метаданных, единый диспетчер выполняет локальную проверку входной строки без DNS-запросов, HTTP-запросов и раскрытия коротких ссылок. Результат — типизированный `ValidatedURL` (платформа, нормализованный URL, тип ресурса, идентификатор), либо код отказа без создания задания. Нормализованный URL не должен изменять смысл ссылки; неоднозначные формы отклоняются.

Проверяются: ровно один URL, ограниченная длина (не более 2048 символов), отсутствие управляющих символов и пробелов внутри URL; только HTTPS; отсутствие credentials, явного порта, IP-literal и фрагмента; точный hostname из §4.1; известная форма пути **отдельного видео** и валидный идентификатор для конкретной платформы; только утверждённые query-параметры без дублей критичных ключей; отсутствие плейлистов, неподдерживаемых сокращателей и произвольных ресурсов. Шаблоны путей и параметры определены §4.1; разработчик фиксирует позитивные и негативные табличные тесты для трёх платформ и не расширяет правила по результатам ошибок `yt-dlp`.

Только диспетчер создаёт утверждённое задание для worker на основе сохранённого состояния SQLite; worker не принимает произвольные URL и аргументы от Telegram или IPC. Callback передаёт только код качества, проверяются владелец и состояние сохранённой карточки, **повторного inspect по callback нет**. Неуспешная `validate_url` означает, что `yt-dlp` вообще не запускается. Проверка пользовательского URL не заменяет фильтрацию исходящих соединений: экстракторы могут обращаться к CDN и URL, полученным от платформ.

- Проверка исходного пользовательского URL и разрешённых доменов обязательна; диспетчер не выполняет HTTP-переходы по перенаправлениям. Сетевая защита от SSRF в v1 имеет **строго ограниченный объём**: для yt-dlp и всех его дочерних процессов блокируются только `127.0.0.0/8` и `::1/128`; прочие частные, link-local, metadata и Fake-IP-адреса не блокируются. Полная защита от SSRF и DNS rebinding не заявляется и отложена до v2 согласно `SECURITY_POLICY_V1.md`, §6 и §9. Домен пользовательской ссылки и домены CDN, используемые `yt-dlp` для загрузки медиаданных, — разные списки назначения; домены CDN нельзя автоматически добавлять в список допустимых пользовательских ссылок.

#### 4.1. Закрытый список разрешённых доменов

**YouTube:**
- `youtube.com`
- `www.youtube.com`
- `m.youtube.com`
- `music.youtube.com`
- `youtu.be`

**Instagram:**
- `instagram.com`
- `www.instagram.com`

**TikTok:**
- `tiktok.com`
- `www.tiktok.com`
- `m.tiktok.com`

**Явно запрещены**, в том числе если они перенаправляют на разрешённый домен:
- `vm.tiktok.com`
- `vt.tiktok.com`
- `instagr.am`

**Разрешённые формы исходных URL v1 (точное совпадение домена и структуры пути):**

| Платформа | Hostname | Допустимый путь |
|---|---|---|
| YouTube | `youtube.com`, `www.youtube.com`, `m.youtube.com`, `music.youtube.com` | `/watch?v=ID` |
| YouTube | `youtu.be` | `/ID` |
| Instagram | `instagram.com`, `www.instagram.com` | `/reel/ID/`, `/p/ID/` |
| TikTok | `tiktok.com`, `www.tiktok.com`, `m.tiktok.com` | `/@user/video/ID` |

`ID` и `user` — валидируемые идентификаторы платформы, а не произвольный путь. Плейлисты, неизвестные формы пути и неутверждённые параметры отклоняются. Для v1 дополнительные query-параметры не допускаются: у YouTube `/watch` обязателен ровно один `v=ID`, без иных параметров; у `youtu.be`, Instagram и TikTok query-строка должна отсутствовать. Параметры `list`, `index`, `t`, `start`, `si`, `feature`, `utm_*` и любые другие отклоняются, а не удаляются молча. Нормализация ограничена безопасным разбором URL и не должна менять идентификатор видео. Расширение этого списка требует изменения ТЗ. Диспетчер **не выполняет HTTP redirects**; запрет коротких доменов действует по исходному hostname. Запросы yt-dlp к CDN/API не проверяются по этому пользовательскому allowlist.

Не разрешать другие домены, сокращатели ссылок, зеркала, произвольные поддомены или новые домены автоматически. Изменение списка допускается только отдельным изменением ТЗ/конфигурации с тестами безопасности.
- В первой версии поддерживаются только материалы, доступные без пользовательской авторизации. Бот не принимает и не использует cookies, пароли, файлы сессий или экспортированные учётные данные. Если источник требует входа в аккаунт, бот сообщает, что скачать материал в текущем режиме невозможно.

Проверка ссылок должна выполнять утверждённую для v1 ограниченную защиту от SSRF, локальную проверку исходного hostname без HTTP-переходов и защиту от инъекций команд. Нельзя передавать пользовательские строки в shell-команды небезопасным способом.

## 5. Анализ видео до скачивания

После получения ссылки бот анализирует метаданные через `yt-dlp` до скачивания полного файла. По возможности определяются название, длительность, миниатюра, доступные форматы и разрешения, аудиодорожки/языки, приблизительный размер вариантов и наличие точных вариантов в кэше.

Если предварительный анализ метаданных не удался, бот уведомляет пользователя, но сама ошибка `inspect` не является автоматическим основанием для отказа в загрузке. Если это безопасно и технически возможно, бот предлагает продолжение без предварительного анализа; не показывает вымышленные качества, размеры, продолжительность или языки аудио. Если безопасное продолжение невозможно, сообщает понятную причину и прекращает дальнейшую обработку. После загрузки до отправки обязательно проверяются фактические продолжительность, формат, размер и целостность медиафайла. При продолжительности более 7200 секунд файл удаляется, пользователь уведомляется. Неизвестный размер обрабатывается по правилу свободного места §10.1. Если `inspect` успешен и известны доступные форматы, показываются только реальные доступные варианты качества. Если метаданные не получены **или** доступные качества определить невозможно, бот показывает ровно две кнопки: «Скачать видео» (режим `video`) и «Скачать аудио» (режим `audio`, результат MP3). Кнопки 480p/720p/1080p/MP3 в таком случае не показываются. Режим `video` означает попытку получить совместимый видеофайл по стандартным правилам проекта без обещания конкретного разрешения; режим `audio` — попытку получить MP3. При невозможности безопасно выбрать и подготовить результат бот сообщает причину и завершает задачу. Для выбранного конкретного качества молчаливая подмена запрещена.

Максимальная длительность видео и аудио — 7200 секунд (2 часа), параметр настраивается в `config.yaml`.

## 6. Пользовательский интерфейс

После анализа бот показывает карточку видео:

- миниатюра;
- название;
- длительность;
- выбранный язык аудио;
- кнопки выбора результата.

Предварительно согласованные варианты:

- 480p;
- 720p;
- 1080p;
- MP3.

Для каждого варианта показывается приблизительный размер файла. Если конкретный вариант уже есть в кэше, он помечается, например, «720p ✓ из кеша». Кеш проверяется отдельно для каждого качества, типа результата, аудиодорожки и параметров обработки.

После выбора варианта кнопки выбора удаляются, чтобы пользователь не мог случайно запустить несколько загрузок повторными нажатиями. Дальнейший статус показывается редактированием существующего статусного сообщения.

Повторное нажатие на ту же кнопку или повторная доставка одного и того же Telegram update не должны создавать новую задачу или повторно выполнять действие. Состояния и допустимые переходы задач контролируются через SQLite; обработка обновлений и callback-действий должна быть идемпотентной. Эта защита не запрещает пользователю намеренно создать новую задачу для того же материала позднее.

Если редактирование невозможно, бот пытается восстановить статус другим сообщением. Статус обновляется только при смене этапа, не по каждому проценту выполнения.

### 6.1. Язык аудио

- Если доступна русская аудиодорожка, выбирать первую подходящую дорожку на русском языке.
- Если русской дорожки нет, использовать оригинальную дорожку.
- Выбранный язык показывать в карточке до выбора качества.
- Если язык определить нельзя, показывать «Язык аудио не определён».
- Дополнительное подтверждение выбора дорожки не требуется.

## 7. Качество и совместимость видео

Рекомендуемое качество по умолчанию — 720p, но пользователь сам выбирает доступный вариант.

При подготовке видео:

- предпочтительный формат — MP4;
- видеокодек — H.264/AVC;
- аудиокодек — AAC-LC;
- если источник уже совместим, избегать лишнего перекодирования;
- если достаточно безопасного remux без перекодирования, использовать его;
- перекодирование выполнять только при необходимости и в пределах настроенных ресурсов.

Видео должно сохранять исходную ориентацию и пропорции кадра. Нельзя обрезать, растягивать или добавлять полосы без необходимости. Портретное видео 720 × 1280 считается вариантом 720p.

**Видео отправляется только как видео в Telegram, не как документ.** Если подходящий формат получить не удалось, бот сообщает об ошибке и не переключается автоматически на отправку документа.

## 8. Аудио и MP3

MP3 — отдельный вариант результата.

- Используется лучшая доступная исходная аудиодорожка с учётом правил выбора языка.
- Для MP3 применяется FFmpeg с настройкой высокого качества, например VBR `-q:a 0`.
- Бот не должен утверждать, что конвертация повышает качество исходного звука.
- MP3 кэшируется отдельно от видео и других вариантов аудио.
- Размер MP3 также проверяется до отправки в Telegram.

## 9. Ограничения Telegram и размер файлов

Первая версия поддерживает облачный Telegram Bot API (`cloud`) и локальный Telegram Bot API Server (`local`). Режим по умолчанию — `local`; режим задаётся явно в `config.yaml`. Бот использует только выбранный режим и соответствующий ему адрес. Автоматическое переключение между `local` и `cloud` запрещено при любых ошибках.

Максимальный размер отправляемого файла зависит от выбранного API и задаётся в конфигурации: начальные значения — `50 MB` для `cloud` и `2000 MB` для `local`. Это пределы API, а не обязательное разрешение боту отправлять файлы такого размера: фактический размер также должен соответствовать прикладным ограничениям проекта. Режим `local` предполагает, что локальный API Server уже установлен, работает и доступен по указанному адресу; его развёртывание и обслуживание не входят в это ТЗ.

В первой версии отдельного прикладного лимита размера файла нет: используется лимит выбранного Telegram API. Размер перед отправкой проверяется по фактическому размеру готового файла; не добавлять к лимиту дополнительный запас или множитель. Если выбранное качество недоступно у источника, показать только реально доступные варианты и предложить пользователю выбрать другой. Если файл превышает лимит выбранного API, также предложить доступные варианты, которые укладываются в лимит. Автоматически повышать или понижать качество либо скачивать другой вариант без согласия нельзя. Если подходящего доступного варианта нет, сообщить об этом.

## 10. Очередь задач

Используются два логических типа заданий: `inspect` (анализ) и `download` (скачивание/обработка). Ограничения ниже относятся к ожидающим заданиям `download`; один worker не выполняет более одной загрузки/обработки одновременно. `inspect` выполняется асинхронно в защищённом worker и может идти одновременно с единственной активной загрузкой; IPC утверждён в §23.4.

| Параметр | Значение |
|---|---:|
| Максимум одновременно обрабатываемых задач | 1 |
| Максимум ожидающих задач | 20 |
| Политика очереди | FIFO с пропуском задач, которым пока не хватает места на диске |
| Тайм-аут ожидания в очереди | 30 минут |

Параметры должны быть настраиваемыми.

Пользователь может отправлять сколько угодно отдельных ссылок, в том числе пока его предыдущие задачи ещё находятся в очереди. Отдельного лимита на число активных задач одного пользователя **не будет**.

Если очередь ожидания заполнена, новая некэшированная задача отклоняется вежливым сообщением. При этом точное совпадение в кэше должно обслуживаться без добавления новой задачи в очередь.

Тайм-аут в 30 минут отсчитывается от момента добавления задачи в очередь. Если за это время задача не начала выполняться, она завершается с понятным сообщением пользователю.

### 10.0. Разделение задач `inspect` и `download`

- `inspect`: получение метаданных, реально доступных качеств и аудиодорожек, ориентировочного размера/продолжительности и возможности подготовки результата. При ошибке действует §5: уведомление и безопасное продолжение, если оно возможно.
- `download`: одна активная загрузка/обработка, максимум 20 ожидающих задач **сверх активной**, ожидание максимум 30 минут с первоначального времени постановки; FIFO с временным пропуском задач при недостатке места без сброса времени ожидания.
- Пока выполняется скачивание, готовый результат другой задачи может отправляться через Telegram, если достаточно места на диске. Отправка не считается второй активной загрузкой/обработкой.
- Пока worker скачивает/обрабатывает задачу A, он может асинхронно выполнять `inspect` задачи B в том же защищённом systemd-юните. Для `inspect` допустимы отдельные дочерние процессы `yt-dlp`, но **не** дополнительные download-worker. Число одновременных `inspect` ограничивается реализацией с учётом ресурсов VPS; состояние заданий и очередь `download` ведёт только основной бот в SQLite.

### 10.1. Проверка свободного места

Перед началом скачивания проверять фактическое свободное место именно на файловой системе, где будут размещены рабочие файлы задачи. Требования не привязаны к общему объёму диска или модели сервера.

**Если размеры потоков известны:**
1. Определить все потоки, необходимые для выбранного варианта. Для раздельных видео- и аудиопотоков учесть размер каждого потока.
2. Рассчитать объём исходных файлов, которые будут одновременно существовать на диске.
3. Учесть дополнительные файлы, которые реально могут сосуществовать при объединении потоков, remux или транскодировании: входные потоки, промежуточные файлы и итоговый файл.
4. Оценить пиковую потребность как сумму размеров файлов, которые могут одновременно занимать место на каждом этапе. Один и тот же физический файл нельзя учитывать дважды, если он переиспользуется; однако итоговый файл нельзя считать равным сумме исходных потоков, если выполняется транскодирование.
5. Начинать задачу только если доступного места достаточно для рассчитанной пиковой потребности. Не применять дополнительные множители или произвольный системный резерв.

**Если размер неизвестен:**
- Использовать `storage.unknown_size_fallback_mib` из `config.yaml`, значение по умолчанию — `2048` MiB.
- Начинать скачивание можно только если свободного места **строго больше 2048 MiB** (или строго больше настроенного значения).
- Это порог допуска к началу загрузки, а не гарантия, что места хватит на весь процесс. Все известные дополнительные потребности обработки всё равно должны учитываться; если по известным данным обработка не поместится, задачу не начинать.

**Если места недостаточно:**
- Не начинать скачивание или обработку, для которой рассчитанной потребности не хватает.
- В очереди временно пропустить такую задачу, дать возможность выполниться следующей подходящей задаче и периодически перепроверять свободное место. Исходное время постановки в очередь не менять; общий срок ожидания остаётся 30 минут.
- По истечении 30 минут завершить ожидающую задачу по правилу тайм-аута очереди и уведомить пользователя.
- Если диск заполнился уже во время скачивания или обработки, безопасно остановить задачу, удалить её временные файлы, сохранить согласованность SQLite, записать ошибку в журнал и уведомить администратора.
- Не вводить дополнительные коэффициенты, множители или резервные пороги, не заданные этими правилами.

В очереди допускается временно пропустить задачу, которой сейчас не хватает места, и запустить следующую задачу, если её условия выполняются. Пропущенная задача остаётся в очереди с исходным временем постановки; бот периодически повторно проверяет условия запуска. По истечении 30 минут ожидания задача завершается с уведомлением пользователя. Максимум один процесс скачивания/обработки одновременно.

## 11. Дневные лимиты

Обычный пользователь получает максимум **3 успешно доставленных новых результата в день**.

- Счётчик списывается только после подтверждённой Telegram успешной отправки нового результата пользователю.
- Неудачные скачивания, обработка с ошибкой, отменённые задачи и неуспешные отправки не расходуют лимит.
- Попадание в кэш по точному совпадению не расходует лимит.
- Лимит рассчитывается по календарным суткам UTC.
- После успешной новой загрузки пользователю показывается остаток дневного лимита.
- Привилегированные пользователи перечисляются владельцем проекта в параметре `trusted_users` файла `config.yaml`. Это настраиваемый список Telegram `user_id` произвольной длины, а не фиксированный список из двух пользователей. Все ID из этого списка имеют неограниченный дневной лимит. Пользователи, не включённые в список, получают обычный лимит.

Список `trusted_users` хранится в `config.yaml`; идентификаторы задаются владельцем проекта локально и не зашиваются в код. Список не должен зависеть от username, поскольку username может меняться. Бот должен иметь команду `/myid`, позволяющую пользователю узнать свой Telegram ID. Изменение списка применяется после предусмотренного перезапуска бота.

Неограниченный лимит не отменяет общую очередь, ограничение диска, тайм-ауты и защиту от перегрузки.

### 11.1. Проверка лимита

Для новой задачи лимит проверяется непосредственно перед началом её обработки, а не в момент получения ссылки. Это позволяет корректно обрабатывать несколько ссылок подряд и кэш-попадания.

После подтверждённой успешной отправки новая загрузка учитывается в лимите не более одного раза. Если Telegram принял файл, а бот завершился до сохранения подтверждения в SQLite, Bot API может не позволить достоверно определить результат; допускается редкая повторная отправка, но повторное списание квоты запрещено. Реализация должна использовать устойчивое состояние задачи и транзакционное обновление квоты, чтобы исключить двойное списание.

## 12. Кэш результатов

Кэш должен хранить метаданные готовых результатов и Telegram `file_id`, чтобы повторно отправлять результат без нового скачивания.

Ключ кэша должен различать:

- платформу и ID исходного видео;
- тип результата — видео или MP3;
- качество;
- выбранную аудиодорожку;
- существенные параметры результата, необходимые для различения вариантов.

Отдельную версию алгоритма обработки в ключ кэша не включать. После обновления программы старые записи кэша сохраняются и продолжают использоваться, пока Telegram принимает соответствующий `file_id`. Поэтому старый кэшированный результат может выдаваться и после изменения параметров обработки; это ожидаемое поведение первой версии.

MP3, видео 480p и видео 720p — разные результаты кэша.

После успешной отправки `file_id` и необходимые метаданные сохраняются в SQLite. Готовый локальный файл сохраняется в приватном каталоге при `storage.keep_downloaded_files: true` и удаляется при `false`. Кэш Telegram `file_id` работает одинаково в обоих режимах; сохранённые локальные файлы не становятся публичными.

Точное кэш-попадание должно обходить очередь скачивания и дневной лимит, но не должно обходить антиспам-лимит ссылок и ограничения Telegram.

При отправке кэшированного результата:
- если отправка успешна, задача завершается без нового скачивания и без расхода дневной квоты;
- если Telegram явно сообщает, что `file_id` недействителен или файл недоступен, запись помечается недействительной, а выбранный вариант ставится в обычную очередь для повторной подготовки;
- восстановление такого результата является продолжением исходного запроса и не списывает дневную квоту повторно;
- при временных ошибках и `429` запись кэша не удаляется, используются обычные правила повторной отправки;
- после успешной повторной отправки новый `file_id` сохраняется в кэше.

Кэшированные записи не удаляются только из-за возраста. Их валидность проверяется при использовании.

## 13. Статусы, тайм-ауты и повторные попытки

Статус показывается в одном сообщении и редактируется при изменении этапа, без обновления каждого процента. Этапы: анализ ссылки, позиция в очереди, скачивание (с номером попытки при повторе), обработка/объединение, конвертация MP3, отправка (номер попытки при повторе), успех или ошибка. Учитывать лимиты Telegram API и `429`.

### 13.1. Скачивание

`max_download_attempts: 3` — максимум 3 попытки всего, включая первую.

- Постоянные ошибки (например, удалённый материал, отсутствие доступа, неверная ссылка, неподдерживаемый контент или нехватка диска) не повторять.
- Временные ошибки повторять в пределах общего лимита.
- Неоднозначную ошибку по возможности классифицировать; если классификация не удаётся, считать её временной и повторять в пределах тех же 3 попыток.
- Перед каждым повтором проверять отмену задачи.
- После исчерпания попыток сообщить пользователю об ошибке, записать подробности в журнал и удалить ненужные временные файлы. Администратору об отдельных ошибках скачивания не уведомлять.
- При аварийном завершении неполный файл удалить и начать скачивание заново, учитывая оставшиеся попытки.

### 13.2. Тайм-ауты

Начальные настраиваемые значения:

| Этап | Значение |
|---|---:|
| Анализ ссылки | 60 секунд |
| Скачивание | 600 секунд |
| Обработка FFmpeg | 1200 секунд |

Тайм-ауты должны быть настраиваемыми через `config.yaml`. Тайм-аут отправки файла не должен быть жёстко установлен слишком коротким значением: учитывать лимиты библиотеки/API и обрабатывать временные ошибки по правилам отправки.

## 14. Отправка готового файла в Telegram

Отправка — отдельный этап с собственными повторами. В режиме `local` отправка и получение файлов должны выполняться через настроенный локальный Bot API с учётом его локальных путей и требований используемой версии `aiogram`; в режиме `cloud` — через облачный API. Для локального режима нельзя строить URL скачивания из абсолютного пути, возвращённого локальным API. Все операции выполняются только в выбранном режиме, включая кэшированные отправки и повторы. Настройки:

```yaml
telegram_upload_max_attempts: 3
telegram_upload_second_attempt_delay_seconds: 30
telegram_upload_third_attempt_delay_seconds: 300
```

- Первая попытка — сразу.
- После первой временной ошибки ждать 30 секунд перед второй попыткой.
- После второй временной ошибки ждать 300 секунд (5 минут) перед третьей попыткой.
- Если Telegram возвращает `429` и `retry_after` больше заданного ожидания, ждать не меньше `retry_after`.
- Постоянные ошибки, например превышение лимита размера, не повторять бессмысленно.
- Сохранять счётчик попыток и время следующей попытки в SQLite; после перезапуска продолжать по сохранённому расписанию.
- После успешной отправки сохранять `file_id` и подтверждение завершения; готовый локальный файл сохранять или удалять согласно `storage.keep_downloaded_files`.
- После третьей неудачной попытки сообщить пользователю об ошибке и удалить локальный файл, если результат не был ранее успешно отправлен и сохранён по настройке.
- Не уведомлять администратора об отдельной окончательной ошибке отправки, если это не системная/критическая ошибка.

Если Telegram принял файл, а бот завершился до сохранения подтверждения, Bot API может не позволить достоверно определить результат. Допускается редкий повторный файл; повторное списание квоты не допускается. Как только Telegram подтвердил успешную отправку, задача считается завершённой и больше не относится к активным задачам бота.

## 15. Отмена задач

В меню бота должна быть команда `/cancel_all`.

Она отменяет все задачи, принадлежащие пользователю, который её вызвал:

- ожидающие в очереди;
- скачиваемые;
- обрабатываемые;
- ожидающие повторной отправки.

Проверка владения выполняется по Telegram `user_id`, а не по username.

При отмене бот должен:

- не запускать дальнейшие этапы задачи;
- по возможности остановить активную загрузку или обработку;
- прекратить будущие попытки отправки;
- удалить временные файлы отменённых задач;
- обновить статус задачи;
- не затрагивать задачи других пользователей.

Если Telegram уже подтвердил успешную отправку, задача завершена и больше не относится к активным задачам бота. `/cancel_all` не пытается отменить или отозвать такой файл.

## 16. Восстановление после аварийного завершения

Состояние незавершённых задач, попыток, расписаний повторов, сообщений статуса и кэша хранится в SQLite. При ручном перезапуске бот сверяет базу с файлами на диске.

- Ожидающие задачи восстанавливаются, если не истёк 30-минутный тайм-аут очереди.
- Незавершённый/неполный файл скачивания удаляется; скачивание начинается заново с учётом оставшихся попыток.
- Готовый файл, который существует и прошёл проверку, отправляется без повторного скачивания и обработки.
- Если готовый файл нельзя проверить, удалить его и повторить скачивание, если задача всё ещё действительна и остались попытки.
- Ожидающая повторной отправки задача продолжает попытки с сохранённым счётчиком и временем.
- Отменённые и завершённые задачи не запускаются повторно.
- После восстановления не отправлять отдельное уведомление о каждом восстановленном задании; уведомление о запуске/перезапуске бота администратору отправляется, если Telegram доступен.

### 16.1. Очистка временных файлов

Настройка `storage.keep_downloaded_files` принимает только `true` или `false` (по умолчанию `false`). При `true` **проверенный готовый медиафайл после подтверждённой успешной отправки** переносится в приватный каталог `botdownload/files` постоянного хранения и не удаляется автоматическими механизмами очистки задач. При `false` такой файл удаляется после подтверждения отправки. Сохранение не распространяется на исходные потоки, промежуточные файлы, повреждённые результаты и частичные загрузки. Каталог хранения должен быть отдельным от временных каталогов задач, недоступным публично, не допускать symlink и произвольных путей. Сохранённые файлы учитываются при проверке свободного места. Автоматическое удаление сохранённых результатов по возрасту не выполняется.

Независимо от настройки обязательны: удаление частичных загрузок и промежуточных файлов при отмене, ошибке и тайм-ауте; удаление повреждённых и непроверенных результатов; безопасная очистка сиротских временных файлов; сохранение проверенного готового файла, пока ожидается повторная отправка или восстановление. После окончательно неуспешной отправки файл не считается успешно доставленным и подлежит очистке в обоих режимах. Значение `true` не отключает защитную очистку и не разрешает сохранять произвольные файлы. Удаление уже сохранённого успешного результата допускается только по отдельной явной административной операции с подтверждением, не через автоматическую очистку временных файлов.

- При каждом запуске сверять временные файлы с задачами SQLite.
- Незавершённые файлы скачивания удалять; проверенные готовые файлы, нужные для возобновления отправки, сохранять.
- Файлы, которые не принадлежат актуальным задачам, удалять только после подтверждения, что они не нужны активным или восстанавливаемым задачам.
- Не выполнять периодическую автоматическую очистку по возрасту.
- Предусмотреть консольную команду для списка сиротских файлов и очистки с режимом `--dry-run`. Команда не должна удалять файлы активных/восстанавливаемых задач. Перед фактическим удалением требовать явное подтверждение; по умолчанию операция отменяется.

## 17. Безопасность, антиспам и логирование

Обязательные меры:

- строгий allowlist YouTube, Instagram и TikTok с проверкой разобранного hostname, а не подстроки;
- принимать только HTTPS, отклонять пользовательские credentials в URL, неожиданные порты, неподдерживаемые схемы, плейлисты и несколько ссылок в одном сообщении;
- соблюдать ограниченную сетевую политику v1: блокировать для yt-dlp и его дочерних процессов только `127.0.0.0/8` и `::1/128`; проверять исходный hostname пользовательских ссылок без HTTP-раскрытия redirects; не заявлять полной защиты от SSRF или DNS rebinding;
- передавать команды `yt-dlp` и FFmpeg списком аргументов без shell; не строить имена файлов из названий видео или пользовательских строк;
- отключить ненужные функции yt-dlp; регулярно обновлять yt-dlp, FFmpeg и зависимости;
- запускать под отдельным непривилегированным системным пользователем;
- не хранить токены в коде или Git и не выводить секреты в логи;
- ограничивать очередь, длительность этапов и обращения пользователя;
- технические логи должны содержать только необходимую диагностику. Не сохранять историю скачиваний, названия видео, содержимое сообщений и полные URL с параметрами.

### 17.1. Лимит ссылок и временная блокировка

Настраиваемые значения в `config.yaml`:

```yaml
rate_limit:
  link_attempts: 5
  window_seconds: 600
  ban_duration_seconds: 3600
```

Первые 5 попыток отправить ссылку в пределах 10-минутного окна разрешены. Попытка № 6 в этом окне запускает блокировку на 1 час. Считаются неверные ссылки, неподдерживаемые платформы, плейлисты и другие попытки отправить ссылку. Лимит привязан к Telegram `user_id` и сохраняется в SQLite, чтобы перезапуск не сбрасывал блокировку. Во время блокировки новые ссылки отклоняются; `/myid` и `/cancel_all` остаются доступными. Уже принятые задачи продолжают выполняться. Пользователь может иметь несколько задач одновременно; отдельного лимита задач на пользователя нет.

Команды и сообщения, не являющиеся попытками отправить ссылку, не учитываются в лимите ссылок. Дневная квота из 3 успешных новых скачиваний действует отдельно.

### 17.2. Уведомления администратора

`admin_telegram_id` задаётся в конфигурации. Уведомлять администратора о:

- успешном запуске/перезапуске;
- критической ошибке базы данных и результате восстановления (успех или неудача);
- критических сбоях, требующих вмешательства;
- низком свободном месте/заполнении диска;
- длительном сбое Telegram — после восстановления соединения, одним сообщением.

Не уведомлять об отдельных неудачных ссылках, обычных ошибках скачивания после трёх попыток и временных блокировках пользователей. Такие события записывать в журнал. Если Telegram недоступен, логировать локально и отправлять уведомление после восстановления связи, если процесс бота продолжает работать. Внешний канал уведомлений в первой версии не используется.

### 17.3. Логирование

```yaml
logging:
  level: INFO
  max_file_size_mb: 5
  backup_count: 3
```

Поддерживаемые уровни: `DEBUG`, `INFO`, `WARNING`, `ERROR`. Ротация: текущий лог и до 3 резервных файлов. Не логировать токены, содержимое `.env`, полные URL с параметрами, содержимое файлов или пользовательские сообщения. Отдельную историю скачиваний не вести.

## 18. Конфигурация

Все изменяемые параметры поведения хранятся в `config.yaml`; секреты — только в `.env`. Изменения конфигурации применяются после перезапуска бота. При ошибках конфигурации бот не запускается и сообщает имена параметров и причины без вывода значений.

`telegram.api_mode` принимает только `local` или `cloud`. Для новой установки значение по умолчанию — `local`. Адреса обоих API явно задаются в конфигурации. Бот использует исключительно адрес выбранного режима; адрес другого режима не является резервным. При недоступности выбранного API бот остаётся запущенным и повторяет попытки подключения с экспоненциальной задержкой от 1 секунды до 300 секунд бесконечно, пока соединение не восстановится или процесс не будет остановлен вручную. Режим не меняется автоматически.

В режиме `local` реализация должна корректно настроить `aiogram` для пользовательского Telegram Bot API Server, включая API endpoint, получение файлов и локальные пути файлов (`is_local=True`, если это предусмотрено используемой версией библиотеки). Нельзя обрабатывать абсолютный локальный путь как HTTPS URL. При старте и последующих запросах запрещено обращаться к API другого режима при любой ошибке.

Начальный набор конфигурации:

```yaml
telegram:
  api_mode: local
  api_base_urls:
    cloud: "https://api.telegram.org"
    local: "http://127.0.0.1:8081"
  max_upload_size_mb:
    cloud: 50
    local: 2000
  reconnect:
    initial_delay_seconds: 1
    max_delay_seconds: 300
    backoff_multiplier: 2

limits:
  max_video_duration_seconds: 7200
  max_audio_duration_seconds: 7200
  daily_download_limit: 3
  max_pending_tasks: 20
  queue_wait_timeout_minutes: 30

storage:
  unknown_size_fallback_mib: 2048
  keep_downloaded_files: false
  files_dir: "files"  # каталог готовых/сохраняемых медиа внутри рабочего каталога botdownload

rate_limit:
  link_attempts: 5
  window_seconds: 600
  ban_duration_seconds: 3600

max_download_attempts: 3
telegram_upload_max_attempts: 3
telegram_upload_second_attempt_delay_seconds: 30
telegram_upload_third_attempt_delay_seconds: 300

timeouts:
  analysis_timeout_seconds: 60
  download_timeout_seconds: 600
  ffmpeg_timeout_seconds: 1200

backup:
  max_copies: 3
  interval_hours: 24

logging:
  level: INFO
  max_file_size_mb: 5
  backup_count: 3

admin_telegram_id: 123456789
trusted_users:
  - 123456789
  - 987654321
```

Это пример структуры и начальных значений, а не реальные идентификаторы пользователей. Реализация должна валидировать типы, допустимые диапазоны и обязательные параметры. Владелец проекта самостоятельно указывает в `trusted_users` Telegram `user_id` всех привилегированных пользователей; список может содержать любое количество ID, в том числе быть пустым. ID не нужно передавать разработчику или публиковать. Пользователи из `trusted_users` имеют неограниченную дневную квоту, но не обходят общую очередь, ограничения диска, тайм-ауты и антиспам.

В первой версии нет отдельного лимита запросов в минуту поверх правила 5 ссылок за 10 минут. Не добавлять `min_system_reserve_mib`, множитель к размеру файла или второй дублирующий лимит загрузки.

## 19. Резервное копирование и восстановление базы

Базу и таблицы SQLite бот создаёт автоматически при первом запуске. Не требуется заранее создавать пустую резервную копию. Резервное копирование выполняется каждые 24 часа во время работы, а также перед обновлением кода и миграциями схемы. Использовать безопасный SQLite Backup API, а не простое копирование открытого файла базы. Хранить до `backup.max_copies` проверенных резервных копий. Старые копии удалять только после успешного создания новой.

### 19.1. Автоматическое восстановление при повреждении

1. Остановить обработку задач.
2. Сохранить повреждённую базу отдельным файлом с именем вроде `database_corrupt_YYYY-MM-DD_HHMMSS.sqlite`; не перезаписывать и не удалять её автоматически.
3. Найти последнюю подходящую резервную копию и непосредственно перед восстановлением проверить её целостность и совместимость со схемой.
4. Если копия исправна, сохранить текущий файл (если он существует), восстановить копию, повторно проверить целостность восстановленной базы и сверить задачи с локальными файлами.
5. После успешного восстановления уведомить администратора и возобновить обработку.
6. Если копии нет или все копии неисправны, сохранить файлы, оставить обработку остановленной, записать причину в журнал и уведомить администратора, если Telegram доступен. Не создавать пустую базу автоматически поверх повреждённой.

### 19.2. Ручные консольные команды базы

В `bot.admin` предусмотреть команды с русскоязычным `--help`. Помимо команд базы данных, должны быть доступны:

- `python -m bot.admin status` — общее состояние бота и базы;
- `python -m bot.admin queue` — текущая очередь и позиции задач;
- `python -m bot.admin disk` — свободное место и состояние временных файлов;
- `python -m bot.admin cache` — количество и состояние записей кэша;
- `python -m bot.admin errors` — сводка последних ошибок;
- `python -m bot.admin tempfiles list` — список файлов-кандидатов на очистку;
- `python -m bot.admin tempfiles clean --dry-run` — показать, что будет удалено, без удаления;
- `python -m bot.admin tempfiles clean` — очистить только подтверждённые сиротские файлы после явного подтверждения.

Для просмотра логов в README описать `tail -F logs/bot.log` и безопасное завершение просмотра через `Ctrl+C`. Для команд справки использовать `python -m bot.admin --help` и `python -m bot.admin <подкоманда> --help`.

Команды базы данных:

- `python -m bot.admin db status` — состояние рабочей базы;
- `python -m bot.admin db backups` — список резервных копий и результаты проверок;
- `python -m bot.admin db check` — проверка рабочей базы и копий без изменения данных;
- `python -m bot.admin db restore --list` — список копий, доступных для восстановления;
- `python -m bot.admin db restore --backup ИМЯ_ФАЙЛА` — выбрать копию, проверить её непосредственно перед восстановлением, показать дату/результат и запросить явное подтверждение;
- `python -m bot.admin db init` — контролируемое создание новой пустой базы, если восстановить существующую невозможно.

Любая разрушительная операция требует явного подтверждения администратора. Ответ по умолчанию — `no`; Enter, пустой ответ или `no` отменяет операцию. Для восстановления использовать явное подтверждение `yes` (или согласованную строку `RESTORE`), после показа пути, даты и результата проверки копии. Команда восстановления должна отказать, если бот запущен. Перед заменой рабочей базы сохранить её отдельно, если она существует. После восстановления проверить целостность ещё раз.

Команда `db init` обязана объяснить, что создание новой базы не восстановит старые квоты, блокировки, кэш и состояние очереди. До создания она должна сохранить все имеющиеся файлы базы и попросить явное подтверждение `yes`. Если существующая база повреждена, сохранить её под именем `database_corrupt_...` и не перезаписывать. Если нет резервной копии, создание новой базы допускается после явного подтверждения; это не должно быть запрещено автоматически.

### 19.3. Неудачное восстановление

Если восстановить базу не удалось, бот не обрабатывает задачи. Администратор получает уведомление об успехе или неудаче, если Telegram доступен; иначе событие записывается в локальный журнал и уведомление может быть отправлено после восстановления соединения. В README описать ручные шаги: остановить бот, сохранить повреждённую базу и все копии, проверить доступные копии, выбрать исправную, восстановить с подтверждением и проверить запуск. Не экспериментировать с оригинальными файлами.

### 19.4. Обновление и откат

Перед обновлением остановить бота, создать и проверить резервную копию базы и зафиксировать текущую версию кода. Если обновление не запускается или не проходит проверки, вернуть предыдущую рабочую версию кода. Не откатывать схему базы автоматически без проверки совместимости; при необходимости использовать проверенную резервную копию с явным подтверждением, учитывая возможную потерю изменений после даты копии.

## 20. Границы самостоятельных решений ИИ-разработчика

Разработчик самостоятельно выбирает лишь внутренние детали внутри утверждённых функциональных границ: названия модулей, совместимые библиотеки, индексы SQLite, локальные алгоритмы и структуру тестов. **Топология процессов, границы ответственности, порядок этапов и обязательные контрольные точки определены разделом 23; менять их без согласования нельзя.** Версии Python и библиотек должны быть совместимыми, зафиксированными в репозитории и описанными в README; обновления зависимостей не должны происходить незаметно.

Разработчик не вправе без согласования менять согласованное поведение, пользовательские лимиты, квоты, правила очереди, кэш, обработку ошибок и повторов, требования безопасности, режим Telegram API или критерии приёмки. Если требование неоднозначно, противоречиво либо технически невыполнимо, разработчик должен описать проблему и последствия, предложить варианты и дождаться решения владельца проекта. Не подменять отсутствующее решение собственным предположением.

Работа ведётся **завершёнными функциональными блоками**, перечисленными в разделе 24. Внутри согласованного блока разработчик последовательно реализует функцию и её необходимые проверки, не запрашивая разрешение на каждый файл или тест. После завершения блока показывает работающий сценарий, изменённые файлы, результаты целевых проверок и ждёт явного разрешения на следующий блок. Не выполнять самостоятельное слияние pull request, развёртывание на сервере, установку дополнительных компонентов или другие внешние действия без согласования.

## 21. Критерии готовности первой версии

Все семь групп приёмочных испытаний обязательны, а также проверка фактического применения безопасности по `SECURITY_POLICY_V1.md`, §10. Дополнительные проверки должны быть привязаны к конкретному требованию этих двух нормативных документов, а не к историческим экспериментам. Дополнительные проверки Telegram API и локальной отправки файлов входят в группу 7 и не образуют отдельные группы. Публичный запуск запрещён, пока все сценарии не пройдены и результаты тестирования не задокументированы.

1. **Основные функции:** скачивание видео и MP3, выбор качества, выбор аудиодорожки, отправка результата.
2. **Очередь и квоты:** FIFO с временным пропуском задач при нехватке места, до 20 ожидающих задач, тайм-аут 30 минут, 3 успешно доставленных новых результата в сутки UTC.
3. **Отмена:** `/cancel_all` отменяет все ещё активные задачи конкретного пользователя.
4. **Восстановление:** перезапуски на разных этапах, SQLite, готовые файлы, счётчики и расписания повторов.
5. **Ошибки и диск:** недостаток места, слишком большой/длинный файл, ошибки скачивания и FFmpeg.
6. **Безопасность:** allowlist пользовательских URL, утверждённая ограниченная SSRF-защита v1, фактически действующий запрет loopback для yt-dlp и дочерних процессов, проверяющий диспетчер, контролируемый worker, отсутствие секретов в логах и административных прав у пользователей.
7. **Telegram и сеть:** потеря соединения, `429`, повторы и восстановление соединения. В эту же группу входят все следующие обязательные сценарии: запуск с `local` использует только локальный endpoint; запуск с `cloud` использует только `https://api.telegram.org`; автоматического переключения между endpoint нет; при недоступности выбранного endpoint процесс продолжает повторные попытки с экспоненциальной задержкой от 1 до 300 секунд до восстановления или ручной остановки; в режиме `local` проверены локальные пути файлов, отправка видео и MP3, работа кэша и повторов. Также проверить повторные нажатия/дублирующиеся updates, восстановление готовых файлов после перезапуска, резервный сценарий при ошибке анализа и отказ от источников, требующих авторизации. Эти сценарии входят в группу 7 и не образуют дополнительные группы.

- [ ] Бот запускается одной командой без аргументов.
- [ ] Настройки читаются из конфигурации, секреты — из `.env`.
- [ ] Поддерживаемые ссылки анализируются, доступные варианты показываются пользователю.

## 22. Инструкция по обновлению проекта в `README.md`

В репозитории должен быть файл `README.md` на русском языке с пошаговой инструкцией по безопасному обновлению бота на Debian 13. Инструкция рассчитана на начинающего пользователя: перед каждой командой объяснить, где её выполнять, что она делает и какой результат ожидается. Не объединять несколько потенциально опасных действий в одну непонятную команду.

### 22.1. Рекомендуемый порядок обновления

1. **Проверить доступ к серверу и репозиторию.** Убедиться, что пользователь находится в каталоге проекта и понимает, какую версию кода собирается установить.
2. **Остановить два сервиса штатно.** README объясняет `systemctl stop tgbot.service tgbot-worker.service`, проверку завершения и безопасное завершение активной задачи; отдельно — ручную диагностику без незащищённых загрузок.
3. **Сделать резервную копию SQLite.** Использовать безопасный способ резервного копирования базы данных. Хранить копию вне каталогов, которые заменяются при обновлении. Соблюдать настройку `backup.max_copies` и оставлять не более заданного числа резервных копий.
4. **Зафиксировать текущую версию кода.** Объяснить, как определить текущий Git-коммит/версию, чтобы при необходимости вернуться к ней.
5. **Получить обновление из GitHub.** Привести подходящий для структуры репозитория способ обновления. Не перезаписывать `.env`, `config.yaml`, базу данных, логи, пользовательские данные и локальные временные файлы. Если есть локальные изменения, сначала остановиться и объяснить пользователю ситуацию — не удалять их автоматически.
6. **Проверить конфигурацию и зависимости.** Объяснить, как активировать существующее виртуальное окружение, установить/обновить зависимости предусмотренным проектом способом и выполнить проверку конфигурации. Не выводить значения параметров, секреты или Telegram ID. При ошибке сообщать название неверного параметра и причину, но не его значение.
7. **Запустить два сервиса через systemd.** Показать `systemctl start tgbot-worker.service tgbot.service`, `systemctl status` и проверку сетевой защиты worker; отдельно документировать ручной запуск для разработки. Объяснить ожидаемое сообщение об успешном старте. При старте бот должен отправить администратору уведомление об успешном запуске/перезапуске, если Telegram доступен.
8. **Проверить работу и логи.** Объяснить, как убедиться, что бот отвечает, задачи восстанавливаются корректно и в логах нет критических ошибок. Временные ошибки пишутся в лог, но сами по себе не отправляются администратору как отдельные уведомления.
9. **Описать откат.** Если обновлённая версия не запускается или тесты после обновления не проходят, остановить бота, вернуть предыдущую версию кода, проверить совместимость схемы SQLite и при необходимости восстановить резервную копию по отдельной осторожной инструкции. До восстановления базы пользователь должен увидеть предупреждение: восстановление может потерять изменения, сделанные после создания копии. Не выполнять восстановление базы автоматически без явного решения оператора.

### 22.2. Требования безопасности к инструкции

- Никогда не просить вставлять токен бота в чат, командную строку, Git или отчёт об ошибке. Токен хранится только в `.env`.
- Не включать `.env`, SQLite, логи, временные файлы и резервные копии базы в Git.
- Не использовать команды, которые без предупреждения удаляют или перезаписывают пользовательские данные.
- Перед потенциально разрушающими действиями объяснять последствия и получать явное разрешение пользователя.
- Использовать два заранее установленных systemd-юнита; не применять динамический `systemd-run`, не давать боту полномочий systemd и не вводить автоматический деплой.
- После обновления проверить конфигурацию, доступность базы данных, восстановление незавершённых задач и возможность ручного запуска.


## 23. Фиксированная архитектура v1

### 23.1. Компоненты и границы

1. **Telegram bot / broker**: получает сообщения, валидирует пользовательский ввод, управляет карточками, очередью, квотами, кэшем, SQLite и отправкой. Не запускает yt-dlp или FFmpeg напрямую.
2. **Единый проверяющий диспетчер**: единственная логическая точка допуска `inspect`, `download`, `cancel`. Проверяет владельца, сохранённый URL, разрешённую операцию, состояние задания и целостность данных. Повторные callback не создают второе задание.
3. **Отдельный worker-процесс**: выполняет только задания, принятые диспетчером; не принимает пользовательские аргументы команд, пути, cookies, proxy или shell. Метаданные и медиа проходят через один и тот же механизм допуска и базовые ограничения.
4. **Локальный IPC**: Unix domain socket с контролируемыми правами, версионированными сообщениями и ограничением размера; без публичного сетевого интерфейса. Worker **не открывает SQLite, не читает её и не изменяет**; все операции с базой, включая запись состояний, выполняет только основной бот. Это архитектурный запрет для кода worker, а не гарантия файловой изоляции при общем UID. Это не гарантия запрета чтения файлов БД на уровне ОС при общем UID.
5. **Один отдельный непривилегированный Linux UID** для бота и worker. Никаких root/sudo, запуска системных сервисов по пользовательскому запросу и дополнительных обязательных UID. Разделение процессов при общем UID не обеспечивает изоляцию секретов на уровне UID: это известный остаточный риск v1. Worker не должен получать токен Telegram, `.env` или данные SQLite через задания; при компрометации worker доступ к файлам, разрешённым тому же UID, всё ещё возможен.
6. **SQLite — единственный источник состояния** очереди, карточек, идемпотентности, попыток, квот и кэша. Только основной процесс бота читает и изменяет SQLite; worker возвращает результаты через IPC и не открывает файл базы.
7. **Рабочие файлы** создаются в приватном каталоге каждой задачи на указанной файловой системе; имена формирует сервис. После завершённой отправки файл сохраняется или удаляется согласно `storage.keep_downloaded_files`; в кэше сохраняется Telegram `file_id`.

### 23.2. Сетевая изоляция и совместимость VPS

- Сетевые соединения **yt-dlp и его дочерних процессов** должны реально блокироваться для `127.0.0.0/8` и `::1/128`. Остальные адреса, включая Fake-IP, не запрещаются сетевой политикой v1.
- Telegram-бот и локальный IPC сохраняют доступ к loopback; локальный Bot API по `127.0.0.1:8081` не должен ломаться из-за ограничений загрузчика.
- Запрет должен быть **обеспечен ОС и проверен в работающем контуре**, а не только проверкой URL в Python или формированием команд.
- Основной утверждённый способ: **два постоянных системных systemd-юнита**. `tgbot.service` сохраняет доступ к локальному Telegram Bot API; `tgbot-worker.service` содержит `IPAddressDeny=127.0.0.0/8` и `IPAddressDeny=::1/128` и запускает `yt-dlp`/FFmpeg только внутри своего cgroup. Оба юнита работают под UID `tgbot`; права на системный systemd им не выдаются. Не использовать `PrivateNetwork=yes` и динамический `systemd-run` в v1.
- Ограничения worker применяются ко всем его дочерним процессам, включая вызовы получения метаданных; bot и worker не должны разделять общий сетевой cgroup. Юниты используют `NoNewPrivileges=true`, `ProtectSystem=full`, `ProtectHome=true`, `PrivateTmp=true`, приватные каталоги данных и дополнительные проверенные ограничения ресурсов; пути IPC и файлов должны быть совместимы с sandbox. `RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6` допускается как дополнительное ограничение, но не заменяет `IPAddressDeny`.
- Перед включением реальных задач установщик/оператор подтверждает поддержку и действие `IPAddressDeny` на данном VPS. Отсутствие нужной поддержки означает отказ от загрузки, а не fallback в незащищённый режим.
- Сервис не требует изменения системного DNS, маршрутов, настройки роутера, специальных IP платформ или Fake-IP. **Не предполагается**, что DNS непременно идёт через Unix-сокет: фактический механизм зависит от VPS. Если DNS использует loopback, совместимость проверяется в worker при действующем запрете; в v1 резервный механизм DNS не специфицируется: поддержка проверена на двух целевых VPS. Если на иной машине DNS/HTTPS не работают при действующем запрете, загрузка не запускается, проблема совместимости сообщается администратору; запрет не снимается.
- Подтверждённые 2026-11-05 ручные проверки на двух VPS: при `IPAddressDeny` DNS и HTTPS работали, доступ к запущенному TCP HTTP-сервису на `127.0.0.1:18765` из ограниченного transient service завершался тайм-аутом, тогда как без ограничения был HTTP 200. Это **предварительное подтверждение совместимости**, а не доказательство DNS через AF_UNIX и не замена приёмки постоянного `tgbot-worker.service`. На одном VPS DNS возвращал Fake-IP `198.18.0.44`, поэтому диапазон `198.18.0.0/15` не блокировать.
- При невозможности применить или подтвердить защиту `inspect`/`download` не выполняются в незащищённом режиме; бот показывает диагностическое состояние.
- Целевая среда: обычный **Linux VPS с Debian 13**, Python/FFmpeg/yt-dlp и доступными необходимыми механизмами ОС; тестовый Debian 12 с Fake-IP проверяется отдельно согласно политике. Под «обычным VPS» не подразумевается гарантия работы на хостинге, запрещающем все необходимые средства изоляции.
- Ресурсные ограничения (память, процессы, CPU, файловая система, длительность, объём результата) обязательны, но конкретные значения должны быть конфигурируемы и соразмерны ресурсам VPS; нельзя требовать исторические значения `MemoryMax=1G` или `RuntimeMaxSec=120` без основания в ТЗ.

### 23.3. Порядок операций

`Telegram update → проверка ссылки → сохранённая карточка → диспетчер inspect → worker metadata → кнопка только с кодом качества → проверка владельца/карточки/состояния → очередь или точное попадание в кэш → диспетчер download → worker yt-dlp/FFmpeg → проверка готового файла → Telegram API выбранного режима → транзакция SQLite → сохранение или удаление готового файла по `keep_downloaded_files` → очистка промежуточных файлов`.

`/cancel_all → проверка владельца → диспетчер cancel → IPC-команда worker → worker останавливает всю группу дочерних процессов yt-dlp/FFmpeg → сообщает результат → бот фиксирует состояние SQLite → очистка`. При недоступности worker бот не объявляет отмену завершённой до подтверждённого прекращения процесса; при потере связи применяется сверка состояния и безопасное восстановление по §23.4.

Ни один обработчик Telegram не передаёт URL в callback и не вызывает загрузчик напрямую. Ошибка отдельного задания не останавливает сервис. При аварии критического компонента, когда невозможно сохранить безопасную работу, загрузки прекращаются до восстановления; не выполняется fallback в незащищённый режим.

### 23.4. IPC v1: минимальный контракт и восстановление

**Транспорт и границы.** Между двумя постоянно работающими systemd-юнитами используется локальный Unix domain socket, не TCP и не публичный порт. Передаются JSON-объекты в UTF-8, одно сообщение на строку (`\n`); протокол имеет поле `version: 1`. Для каждого сообщения обязательны `request_id` (идентификатор обмена), `task_id` (идентификатор задания в SQLite) и `action` для запроса либо `status` для ответа. Максимальный размер одного сообщения — 64 КиБ; некорректный JSON, неизвестная версия, команда, поля или превышение лимита отклоняются без запуска инструментов. Права на socket и его каталог ограничиваются учётной записью сервиса; socket размещается в доступном обоим юнитам каталоге, не в `/tmp` (из-за `PrivateTmp=true`). Абсолютный путь определяется при установке и одинаков для обоих юнитов.

**Команды от основного бота:**

- `inspect`: анализ ранее проверенной и утверждённой ссылки, получение метаданных и доступных форматов;
- `download`: загрузка и обработка по сохранённому заданию и выбранному допустимому коду формата либо по согласованному режиму `video`/`audio` без метаданных;
- `cancel`: запрос отмены задания и остановки принадлежащей ему группы дочерних процессов;
- `status`: запрос текущего состояния конкретного задания для сверки после переподключения.

**Минимальные поля и ответы.** Запрос содержит `version`, `request_id`, `task_id`, `action`, `payload`. `payload` содержит только необходимые проверенные данные задания: для `inspect`/`download` — нормализованный URL, платформу, идентификатор ресурса и разрешённый код формата/режима, когда он нужен; для `cancel`/`status` — пустой объект. Worker повторно проверяет допустимость операции, структуры задания и URL перед любым вызовом `yt-dlp`, не принимает произвольные CLI-аргументы, shell-команды, пользовательские пути, cookies или proxy. Ответ содержит `version`, `request_id`, `task_id`, `status` (`accepted`, `running`, `completed`, `failed`, `cancelled` или `not_found`) и при необходимости `result` либо `error` с машинным кодом и безопасным текстом. `accepted` подтверждает приём, но не завершение операции; итоговое состояние сообщается отдельно. Результат `inspect` содержит только полученные фактические метаданные/форматы; результат `download` — сведения о готовом файле и результатах проверки, без передачи произвольного пути от пользователя. Секреты, Telegram-токен и содержимое SQLite через IPC не передаются. Конкретные имена Python-классов и внутренних функций не регламентируются.

**Параллелизм.** Пока единственная операция `download`/FFmpeg выполняется, worker может асинхронно выполнять `inspect` для других заданий в том же защищённом сервисе. Это не создаёт дополнительных download-worker. Одновременные `inspect` ограничиваются настройкой/внутренним лимитом ресурсов. Очередью загрузок, лимитом 20 ожидающих задач, 30-минутным сроком ожидания и состояниями в SQLite управляет исключительно основной бот. Отправка уже готового файла в Telegram может идти параллельно следующей загрузке при достаточном свободном месте.

**Отмена, повторы и рестарт.** Бот фиксирует намерение отмены в SQLite и посылает `cancel`; worker прекращает операцию и её дочерние процессы и возвращает `cancelled` только после подтверждения остановки. При потере соединения бот не считает задачу завершённой или отменённой по одному факту разрыва и не запускает вторую копию загрузки. После переподключения бот запрашивает `status` для незавершённых задач, сопоставляет ответы с SQLite и файлами, затем решает о безопасном продолжении, повторе или ошибке согласно общим правилам восстановления. Если worker перезапустился и сообщает `not_found`, бот сначала проверяет результаты на диске и лишь затем повторно ставит задачу с соблюдением лимитов попыток; если состояние неопределённо, новая загрузка не стартует до устранения неопределённости. `request_id` связывает ответ с запросом, `task_id` — с единственным заданием; повтор команды не должен создавать параллельную копию операции с тем же `task_id`. **SQLite открывает, читает и изменяет только основной бот; worker не имеет SQLite-клиента.**

## 24. Порядок разработки: законченные функциональные блоки

Каждый блок считается завершённым, когда работает указанный сквозной сценарий, пройдены **целевые** проверки и нет известных критических дефектов данного блока. Не требуется расширять набор тестов сверх требований ТЗ и политики; общая регрессия выполняется после существенных интеграционных изменений и перед финальной приёмкой. Нельзя заменять готовую пользовательскую функцию десятками дополнительных тестов вспомогательных абстракций.

1. **Основа и состояние**: конфигурация, запуск, SQLite, схема задач, логи, `doctor`, безопасные рабочие каталоги. Демонстрация: штатные systemd-юниты запускаются, ручной запуск бота доступен для диагностики, ошибочная конфигурация объясняется, состояние переживает рестарт.
2. **Ввод, карточки, метаданные**: allowlist, единый диспетчер, worker, изоляция inspect, безопасные метаданные, кнопки без URL. Демонстрация: реальная ссылка → карточка YouTube/Instagram/TikTok при доступности источника; неизвестный URL отклонён. **Сетевой допуск обязателен уже на этом этапе.**
3. **Загрузка и обработка**: очередь, дисковый допуск, yt-dlp, FFmpeg, MP4/MP3, ограничения ресурсов, проверка результата, отмена дерева процессов. Демонстрация: выбранное качество → готовый проверенный файл, отмена останавливает процесс и удаляет частичные файлы.
4. **Telegram-доставка и кэш**: режимы cloud/local, отправка, независимые повторы, сохранение `file_id`, сохранение или удаление готового файла по конфигурации, кэш-попадание, квоты. Демонстрация: ссылка → выбор → доставка → повторная отправка из кэша без скачивания.
5. **Надёжность и эксплуатация**: восстановление SQLite и файлов, резервные копии, админ-команды, антиспам, уведомления, инструкции обновления двух systemd-сервисов. Демонстрация: рестарт во время очереди/загрузки/отправки и безопасное восстановление без двойного списания.
6. **Финальная интеграция и приёмка**: семь групп §21 плюс все проверки §10 `SECURITY_POLICY_V1.md`, включая фактическую сетевую изоляцию на обычном VPS и отдельную проверку Debian 12 с Fake-IP. Результат: протокол PASS/FAIL/INCONCLUSIVE с доказательствами; незавершённые обязательные проверки не объявлять пройденными.

**Правило остановки тестирования:** для каждого требования достаточно установленного набора проверок, который подтверждает его выполнение; новые тесты добавляются при обнаруженном дефекте, изменении поведения или непокрытом обязательном сценарии. После PASS критерий не открывается заново без причины. Не добавлять обязательные требования из исторических документов.

**Правило изменений:** если обнаружена техническая невозможность или противоречие между этими двумя документами, разработчик останавливает затронутый блок, формулирует конкретное решение и получает согласие владельца. Самостоятельно ослаблять политику или расширять v1 нельзя.

### Уточнение v1: каталог файлов

Рабочий каталог приложения — `botdownload` (фактический абсолютный путь выбирается при установке). Каталог готовых и сохраняемых медиа — `botdownload/files`, задаётся `storage.files_dir: "files"` относительно рабочего каталога. Каталог должен создаваться с приватными правами, без доступа посторонних пользователей; пути файлов формирует приложение, пользователь не может задавать их напрямую. Временные и частичные файлы размещаются отдельно от готовых результатов и обязательно очищаются согласно политике. Разработчик выбирает безопасные пути Unix-сокета, SQLite и временных файлов при установке: socket — в общем приватном runtime-каталоге, доступном обоим юнитам (не `/tmp`), SQLite — в приватном постоянном каталоге основного бота, временные файлы — отдельно от `files`. Права и настройки systemd должны обеспечивать штатную работу двух сервисов; worker не открывает SQLite. Дополнительное согласование конкретных абсолютных путей не требуется.
