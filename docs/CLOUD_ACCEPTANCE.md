# Самостоятельная приёмка: сначала Debian 13 + cloud

Рабочий план, не нормативный документ. ТЗ и политика безопасности не изменяются.
Утверждённый пользователем порядок: Debian 13/cloud → затем local → Debian 12/Fake-IP.
Разработчику не передаются SSH-доступ и токен. Результаты фактически выполненной частичной приёмки Debian 12 приведены ниже.
Остальные сценарии сохраняют статус **INCONCLUSIVE**.

## Правила сеанса

- Одна небольшая группа команд; затем результат и разбор, только потом следующий шаг.
- Каждая группа указывает SSH-каталог/пользователя, ожидаемый результат и остановку при ошибке.
- Никаких автоматических удалений, рекурсивных chown/chmod, перезаписи .env/config/БД,
  переустановки поверх неизвестного проекта или отключения защиты.
- Не отправлять .env, токены, содержимое config.yaml с реальными ID, cookies, ключи SSH.
- Результат PASS относится только к конкретной выполненной проверке. OBSERVED пробы
  не заменяет разбор baseline/юнита и не разрешает объявить весь сервис готовым.

## Первый шаг — только диагностика среды

Где: SSH-терминал на целевом VPS, любой каталог, текущая учётная запись.
Команды ничего не устанавливают, не меняют файлы и не останавливают сервисы.

```bash
cat /etc/os-release
uname -r
ps -p 1 -o comm=
id -u
```

Ожидаем: Debian (`ID=debian`), версия `13`, PID 1 — `systemd`. Последняя команда
печатает только числовой Linux UID: `0` означает root, другое число — обычную
учётную запись; наличие sudo проверяется отдельно следующим шагом при необходимости.
При ошибке/другой системе остановиться и прислать обезличенный вывод, не пытаться
менять init или обновлять ОС по догадке.

## Следующие этапы (команды выдаются после разбора результатов)

1. Проверить полномочия и обнаружить существующий проект/UID/юниты, не читая секреты.
2. Выбрать новую установку либо безопасное обновление с сохранением данных.
3. Сверить Git-коммит, установить зависимости, проверить владельцев/права. Новые
   runtime-каталоги (включая logs до первого старта) — tgbot:tgbot 0700;
   .env/config — 0600. Исходники и .venv принадлежат администратору и доступны
   tgbot только для чтения/исполнения. Venv symlink на системный Python допустим.
4. Проверить default cloud/официальный endpoint и локально задать токен; содержимое файлов не публиковать.
5. Установить два постоянных юнита с ресурсами по VPS и root-owned утилиту подтверждения.
6. Подготовить root-запрос, оба непрерывно работающих TCP baseline вне worker,
   выполнить пробу в окончательном постоянном worker без изменения unit после неё.
7. Разобрать отчёт родителя/детей IPv4/IPv6, DNS/HTTPS; helper проверяет свежесть,
   boot, hash, InvocationID и оба baseline под тем же UID. Только после этого
   оператор может явно подтвердить изоляцию; проба/подтверждение не выполнялись разработчиком.
8. Архивировать тестовый запрос/доказательства, завершить только временные HTTP-фикстуры.
9. Проверить /myid, карточки/кнопки трёх платформ, фактические MP4/MP3 через cloud,
   выбранный язык/качество, лимит размера без молчаливой подмены, обработку ошибок.
10. Проверить независимые ссылки/дубли callback, очередь/FIFO/диск/тайм-аут,
    квоты/кэш/антиспам, отмену, рестарты и восстановление, оба режима хранения.
    Опасные сценарии порчи БД/диска — только на отдельной тестовой копии, никогда
    не повреждать/заполнять рабочий сервер ради испытания.
11. Проверить повторы/429/длительный сбой Telegram доступными контролируемыми
    способами; не подделывать Telegram 429 как фактический ответ официального API.
    Невыполненные сценарии остаются INCONCLUSIVE.
12. Зафиксировать результаты cloud. Затем отдельно проверить local и Debian 12/Fake-IP.

## Текущее состояние — частичная приёмка Debian 12

Дата проверки: 2026-11-07. Среда: Debian 12 (Bookworm), Python 3.11.2,
systemd 252, FFmpeg 5.1.9; Telegram API — `cloud`.
Это отчёт по результатам, переданным оператором из VPS, а не самостоятельное
подключение разработчика к серверу. Секреты и личные идентификаторы не публикуются.

**Подтверждено оператором:**

- Два постоянных systemd-сервиса `tgbot.service` и `tgbot-worker.service`
  запускались от `tgbot`, были `active (running)` без рестартов.
- Для постоянного worker проверены блокировки IPv4 и IPv6 loopback в родителе
  и дочерних процессах, при работающих baseline-серверах; DNS/HTTPS прошли.
  Root-helper сверил доказательства и подтвердил изоляцию. Доказательства
  сохранены локально оператором вне репозитория; исходники unit после пробы
  не изменялись.
- Telegram-бот успешно анализировал ссылку, показывал варианты, обновлял
  статусы и отправлял видео. Повторный запрос был обслужен из кэша.
- Для первого запуска потребовалось создать приватный каталог `logs`
  (`tgbot:tgbot`, `0700`) и указать полный Telegram-токен в локальном `.env`.
  Эти значения и содержимое `.env` не включаются в репозиторий.

**Не подтверждено как полная приёмка:** все платформы и форматы MP4/MP3,
лимиты/очереди/отмены, сценарии Telegram 429 и отказов, восстановление БД,
режим `local`, Debian 13 и специфичные сценарии Fake-IP. Их статус —
**INCONCLUSIVE**, пока оператор не проведёт отдельные проверки.

Оператор остановил службы для проверки следующего обновления. Автозапуск
на момент проверки не включался. Это не свидетельствует о неисправности бота.
